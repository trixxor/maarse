Privacy and security

What is protected, what is not, and who you still have to trust.

TL;DR

What: messages are end-to-end encrypted and the sender is never written in a packet header. Your address is a hash of your public key, so nobody hands you an identity and nobody can take it away.

Why it matters: radio is a broadcast medium. Anyone with a receiver in range hears every packet, so the design assumes the listener is always there.

Advantages

  • Well-known building blocks (X25519, ChaCha20-Poly1305, Ed25519)
  • Sender hidden inside the encrypted message
  • Announces and path requests need a small proof of work, which makes spam costly
  • Firmware and alerts are signed

Good to know

  • Not reviewed by outside experts
  • No anonymity: who talks to whom is visible
  • Channel senders are not authenticated
  • Host history is stored unencrypted by default

working copy Do not rely on Må:rse for anything where a break would cause harm.

What a listener can read

Someone with a LoRa receiver and no keys can read this from a direct message:

Readable without a key
MeshtasticSender and recipient node numbers, packet id, channel hash, hop counts
MeshCoreShort hashes of recipient and sender, and the repeaters on the path
ReticulumThe recipient's destination hash; no sender address
Må:rseThe recipient's 16-byte address and the path; the sender is never in the header
No anonymity

Må:rse protects content and hides the sender inside the message. It does not hide the fact that two nodes are communicating, and it does not hide the recipient's address. Position and telemetry are off by default, and rounded to a grid when shared.

Your identity

You get an identity the first time the app or host starts: two key pairs, one for signing and one for key agreement. Your address is a hash of both public keys, and it is the same over radio, TCP and the internet.

  • Recovery phrase: 24 words let you restore the identity. Anyone with the phrase is you, and the project does not store it.
  • Safety number: a 60-digit number two people can compare, for example with QR codes, to check nobody is in the middle. It only protects you if you actually compare it.

Channels and alerts

  • Channels use a shared key. The keys of the public channel and of #hashtag channels are derived from the name, so anyone can read them. Private channels need the key to be shared.
  • The sender of a channel message is not authenticated. Anyone holding the key can write as anyone. Signing is noted as a later improvement.
  • Public alerts are signed by issuer keys and shown as a banner no chat message can imitate. Receivers trust only the root keys they are configured with.

What you still have to trust

The release signing keySign firmware that every node trusting it will install. A new key means visiting every node.

Known weaknesses
  1. The cryptography has not been externally reviewed, and the forward-secrecy ratchet is a draft.
  2. Channel senders are unauthenticated.
  3. Host history is stored unencrypted on disk by default, and kept 90 days.
  4. Any local program can reach a host on loopback unless it requires an access key.
  5. No closed networks yet: any node can route through any repeater.
  6. Jamming the radio band cannot be prevented by any protocol.

The cryptography in detail

Source: maarse-crypto/src/*, spec section 6. working copy Not externally reviewed.

Primitives: Ed25519 (signatures), X25519 (key agreement), SHA-256, HKDF-SHA256, ChaCha20-Poly1305 (96-bit nonce, 128-bit tag), and PBKDF2-HMAC-SHA512 for the recovery phrase only. Every decoder is fuzzed, and the project's own crates forbid unsafe code.

Identity and address

The secret form is 64 bytes: the Ed25519 seed (32) and the X25519 secret (32). The public form is the two public keys (64 bytes). The address is the first 16 bytes of SHA-256(Ed25519 public | X25519 public).

The static seal

A direct message without a session is sealed one-way in the style of Noise X:

e_pub (32) | sender address XOR k1 (16) | ChaCha20-Poly1305(k2, message) | tag (16)

es = X25519(e, R_dh)          ss = X25519(S_dh, R_dh)
k1 = HKDF(salt "maarse/dm/v0/sender", ikm es,      info e_pub | R_addr)           -- 16 bytes
k2 = HKDF(salt "maarse/dm/v0",        ikm es | ss, info e_pub | R_addr | S_addr)  -- 32 bytes
nonce = 12 zero bytes;  AAD = the first 48 bytes

The overhead is 64 bytes, so the largest message is 212 − 64 = 148 bytes. A fresh ephemeral key e is used for every message, so the zero nonce is safe. Only the recipient can recover the sender address, and the recipient needs the sender's public keys, normally from an announce, to verify the ss part. Non-contributory Diffie-Hellman results are rejected.

Forward secrecy

Contacts that support it use a ratchet. draft A leaked current key exposes the current session. Mail held in post offices is sealed with the static format, without forward secrecy.

Proof-of-work stamps

Announces need a stamp of about 0.3 s on an nRF52840. Path requests, key requests, mail syncs and deposits use a smaller 8-bit stamp: cheap for one message, costly for a flooder, but a determined attacker can still use airtime.

Safety numbers

The safety number hashes the public keys 512 times, turns the result into 6 groups of 5 digits, and concatenates the two people's fingerprints in sorted order, giving 60 digits.

Signed things

  • Firmware updates: an Ed25519-signed manifest. A node installs only for its own board, a newer version, and a signature matching its built-in release key. Updates are disabled with a missing, weak or development key.
  • Releases: SHA256SUMS signed with the release key.
  • Bulletins and alerts: signed by issuer keys with certificates from a root key that limit what an issuer may send, expiry, and serial numbers against replays.
