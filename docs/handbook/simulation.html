Evidence · Measurements

Simulation results

What the simulator says, run fresh, with what it does and does not prove.

TL;DR

What: The Må:rse simulator runs the real router code in many virtual nodes, with a radio model, on maps of Denmark. This page shows what it says, run fresh on 2026-11-27, with what each result does and does not prove.

Why: Nobody has measured Må:rse outdoors yet. The simulator is how design choices were compared before hardware: which fix helped, which one was rejected, and what each cost in airtime.

Strengths

  • Same router code as the radios, so a result says something about the real decision logic
  • Every chart on this page is a measured run with the seeds and the script named
  • Rejected ideas stay in the record with their numbers
  • Run it yourself in the browser, or with node tools/sim-experiments/…

Good to know

  • It is a model: a log-distance path-loss model with exponent 3, not real terrain and interference
  • It was optimistic in the past: honest packet sizes moved the E45 car result from 97 % to 81 %
  • A few scenarios (national, outage) have moved over time, and some numbers in older documents are out of date
  • Four to seven seeds per scenario: differences under about 5 % are noise

simulated everything on this page. Nothing is field-tested.

What the simulator is

The scenarios are on a map of Denmark: a national network with about 800 nodes, 10 walkers in Rold Skov, 300 handhelds in Aarhus, a car on the E45, and a traveller from Aalborg to Rønne. A scenario runs for 45 minutes to 8 hours of simulated time, with messages between friends, and the simulator counts what arrived, how long it took, and how many seconds of radio time were used. Airtime is the budget: it is shared and limited by law.

How to read a percentage

86 % delivered means: of all messages created in the run, 86 % had reached the recipient before the run ended. The window is fixed by the scenario (45 minutes for the forest and town, 8 hours for the crisis). A message sent late and still on its way at the end counts as not delivered, so the number is not "14 % lost for ever".

It is also not a promise that everything arrives given enough time. In the real system a message is retried twice and then dropped or carried. A carried copy lives 30 minutes, and mail in a post office lives 7 days, at most 100 messages per recipient. After that it is gone.

  • Delivered is the share of messages that had arrived when the run ended, acknowledged the share where the sender also saw the confirmation.
  • Airtime is the sum of every node's transmitting time, in seconds.
  • You can run the same engine in the Denmark simulator and compare in the Mesh Lab.

Where the airtime goes

Share of airtime by packet type

Today's defaults, five scenarios, mean of 4 to 7 seeds.

In every scenario but the car, path requests are the largest line, 44 to 65 % of the airtime. Announces are 11 to 24 %. Only the moving car spends most of its airtime on data.

Source: tools/sim-experiments/airtime_round.mjs all 5 honest,c_old,c_new, config c_new, run 2026-11-27 on the committed engine.

This is why the project works on fewer packets and not only smaller ones. A message with a known route is cheap. Discovering a route is not.

What today's defaults changed

Two changes went into the defaults on 2026-11-26: a compact frame that cuts encryption overhead from 69 to about 34 bytes, and path request tuning: retry after 20 s instead of 45 s, and a node with at least three neighbours forwards 80 % of the path requests it hears. Each was run in the same five scenarios, one at a time.

Path request tuning: today against the old retry and forwarding settings

Both runs use the compact frame. Bars show the change in airtime; the note shows delivery before and after.

Tuning saved airtime in all five scenarios, from 2 % in the town to 25 % in the car, and lifted the car from 90.2 % to 96.9 % delivered. This is the change that helps where path requests dominate.

Source: tools/sim-experiments/airtime_round.mjs all 5 honest,c_old,c_new, c_old against c_new, run 2026-11-27. 4 to 7 seeds.

The compact frame: 34 bytes of overhead against 69

Both runs use today's path request settings.

In today's engine the compact frame saved 11 % in the forest and about 2 % elsewhere, and cost about 3 % in the car. That is much less than the report's 17 % and 30 %, which was measured on an earlier engine. The sign is stable. The size of the effect is not.

Same run, honest (69 bytes) against c_new (34 bytes).

Read this before quoting a number

These are 4 to 7 seeds each. Differences under about 5 % are noise. The national and outage scenarios are in a duty-cycle-saturated regime, where small changes make delivery jump. The effect of the compact frame in this run differs from the report's, because the committed engine has changed since the report was written.

What the compact frame and the other airtime ideas gave

What each chain fix did

In November the whole chain, from a handheld in a forest through a bridge, a repeater, a host and the TCP backbone to another host, was reviewed and fixed in a series of changes. This run adds them one at a time on top of each other, starting from what ran on the boards before the review.

Car on the E45: delivered, step by step

Percent delivered after each change was added.

One change decides this scenario: the queue fix, which stops the firmware from queuing a second copy of a packet that is already waiting. Behind the duty cycle the copies piled up and each made the previous hop resend. 70 % became 96 %.

Source: tools/sim-experiments/final.mjs, results file final-results.json (engine of 2026-11-16, 6 to 8 seeds).

Carry: when nobody can hear anyone

A crisis scenario: the national network is hit at time zero. There is no internet, everything within 25 km of Aarhus, Odense, Copenhagen and Aalborg is destroyed, and a third of the remaining repeaters are gone. Thirty handhelds drive between towns at 70 km/h, and people write messages for 6 hours. Share delivered, by distance between sender and recipient.

Carry in a crisis: delivered by distance

Percent delivered after 8 simulated hours, mean of 3 seeds.

Carry helps most at middle distances: 66 to 76 % at 25 to 100 km. Over 100 km it moves 9 to 14 %. Keeping messages 6 hours with room for 64 does not do better in this run, and costs much more airtime.

Source: tools/sim-experiments/crisis.mjs, run 2026-11-27.

Carry in a crisis: airtime

Seconds of radio time, all nodes.

Carry as the firmware has it costs about 24 % more airtime in this run. Longer lifetime and more room raises it to about 80 % more than no carry, for no gain.

Mail for people who are offline

A traveller lives in Aalborg, switches the phone off at 20 minutes, travels to Rønne on Bornholm, and switches it on again at 70 minutes. Friends write every two minutes. The chart shows the share of the messages written while the phone was off that arrived.

Mail while the phone is off

Percent of the messages written during the offline period that arrived. Mean of 3 seeds.

With the internet up, post offices take mail for an offline traveller from 4 % to 76 %, and 88 % with repeaters acting as small offices. The older design with one named home host reached 36 %. With the internet down, post offices still give 39 %, against 3 to 4 % for the others.

Source: tools/sim-experiments/journey.mjs, run 2026-11-27. The national preset with both LoRa trunks.

What the post offices cost in this run

Airtime in seconds, and delivery of messages written after the traveller was back on air on Bornholm.

Post offices are not free in this model: about 2.5 times the airtime, and delivery to the traveller once on Bornholm fell from 99 % to 54 %. The run does not explain why. It is a warning, and an open item, not a verdict.

Same run. Internet up.

A number that changed

Earlier documents quote that with the internet down 98 % of a traveller's mail reaches Bornholm. In today's engine the same scenario gives about 36 to 39 %. The older figure came from an engine before the height map and before host-to-host mail moved to radio when no TCP link exists. The project's own report lists this as a possible model gap and has not resolved it.

Long-distance LoRa trunks

Two directional LoRa links between hosts (Aarhus to Zealand, Zealand to Bornholm), run with and without internet. 30 % of messages go to users anywhere in the country, so many cross the water.

Messages across the water

Percent delivered across the water. Higher is better.

With the internet up the trunks add about 9 points as a backup (39 to 48 %) at almost no airtime cost. With the internet down, the trunks lift crossing the water from 2.5 % to 11 to 15 %. That is better, but still low: a trunk is a backup, not a replacement for the internet.

Source: tools/sim-experiments/trunks.mjs, run 2026-11-27.

What the simulator cannot say

  • Real range, interference, antennas and weather. Nothing is field-tested.
  • Whether a firmware change behaves on a board as in the model. Two boards on a desk have been tested.
  • Anything that needs more seeds: differences under about 5 % are not distinguishable from noise.
  • Files, voice and pages are not in these scenarios.

Reproduce a result

The scripts live in tools/sim-experiments/. They load the engine from docs/denmark/maarse_sim_wasm.wasm or the build in target/wasm32-unknown-unknown/release/.

node tools/sim-experiments/airtime_round.mjs all 5 honest,c_old,c_new   # airtime, honest sizes
node tools/sim-experiments/forest_mode.mjs both 2700 1,2,3,4,5          # roles in forest and town
node tools/sim-experiments/crisis.mjs                                   # carry in a crisis
node tools/sim-experiments/journey.mjs                                  # mail for a traveller
node tools/sim-experiments/trunks.mjs                                   # LoRa trunks
node tools/sim-experiments/final.mjs                                    # the chain fixes

On Windows run the commands in a shell with Node installed. Each can take several minutes. The raw outputs behind this page are the lines these scripts print.

Model details

  • Radio: log-distance path loss with exponent 3, SF9, 125 kHz, coding rate 4/5, 10 % duty cycle. The "honest" config uses preamble 16 and a 69-byte seal. Hills and a height map are included since 2026-11-19.
  • maarse-hostrules carries the host's decisions into the simulator, so hosts in the simulation make the same choices as the real host.
  • The simulator reports delivered, acknowledged, median latency, transmissions, airtime and airtime by packet type.
Source: runs of tools/sim-experiments/*.mjs on 2026-11-27 on the committed engine, the airtime report docs/maybe/airtime-optimisation.md, and final-results.json.
