Get started

Må:rse is a message network for LoRa radios and computers. A local group can communicate with matching radios and a usable path. Hosts can connect radio groups over an IP backbone, or operate over IP alone. A browser or Android app is the interface you use to read and send messages. The radio or host behind it supplies the network identity and routes the packets.

Send your first message

  1. Start two hosts or connect two clients to separate radios. For a host-only trial, link the hosts over TCP. For a radio-only trial, keep both radios close and match their regional settings, frequency, bandwidth and spreading factor.
  2. Open the client connected to your own node. Read its address and exchange addresses with the other person. Select the contact or use the address field to open a direct conversation.
  3. Send a short message. Check the receiver’s conversation and wait for the delivery receipt on the sender. Compare safety numbers if you need to verify the identity.
  4. If delivery fails, check client connection first, then check whether either node has heard the other. Use traces or the server dashboard when a gateway sits in the middle.
# From the repository on Windows
.\scripts\start-host.bat
# From the repository on Linux
./scripts/start-host.sh

The ordinary host serves its web interface at http://127.0.0.1:8080/ by default. Setup and access details vary by build and mode. See host operation for public web access, credentials and deployment.

Connect and recover a session

Use the client’s connection screen to choose a host, USB or Bluetooth. Plug in a data-capable cable for USB. For Bluetooth, keep the radio within range and allow the permissions requested by the client. If you reconnect to a different node, expect a different node address and potentially a different local conversation history. A host access key authorizes the connection to that particular host. Account recovery material and the access key serve different purposes.

Install the browser client as a PWA from a compatible browser if you want a separate app window. A cached client can open while the network is unavailable. Sending still requires an active route through a host or radio. Check which node the interface shows as connected before troubleshooting message delivery.

History and local data

Several browser windows connected to one host can read that host’s history. This is useful when a computer remains on and several screens use the same node. Linked-device accounts connect separate nodes and use sibling sync, described under identity and accounts. A host’s data directory contains identity, history and settings. Protect it as you would the node itself.

Messages, contacts and channels

Direct messages and delivery states

Start a direct conversation with a node address or linked account. The sender needs the recipient’s public identity. If it lacks that identity, it can request keys through the mesh. A displayed name is a label. Use the address or a verified safety number when identity matters.

StatusMeaningWhat to check
Pending or waitingThe client or node is still trying to send or get a receipt.Verify the current connection and wait for route discovery.
DeliveredThe sending node saw a delivery receipt for the message.Delivery confirms receipt by a node. There is no implication that a person has read it.
CarriedStore-carry-forward helped the message or receipt cross a temporary gap.Delivery speed depends on when the networks or nodes meet again.
Waiting in a post officeA host accepted the message for offline delivery.Storage and replica availability determine how long it can be handed over.
FailedThe client or node reported a send failure.Read the error and check the recipient’s key, node reachability, or the chosen transport.

Text is optimized for short messages. Compression can reduce airtime for suitable input, and the practical text budget can depend on packet overhead. Send long text or media as a file. Capable hosts can number messages per conversation and display a gap when earlier numbered messages have yet to arrive.

Contacts and names

Hear or add a node, open its details and choose to message it. Locally assigned contact names help identify conversations and can take precedence over announced names. A display name is shared in announcements and can be copied by anyone. Capable firmware retains selected contacts and persistently stores their public identities so those nodes can be recognized after a restart.

Public, hashtag, private and regional channels

Use a channel when a message is intended for a group. Public and hashtag channels have publicly derivable keys, so anyone can read or send to them. A private channel uses a shared secret. Give it only to intended participants and rotate it after a loss of access. A shared key gives every participant the ability to write, and displayed sender names have no independent authentication. Channels do not provide a direct-message-style receipt from every recipient.

A regional channel adds a forwarding scope. Nodes configured for regions can restrict where eligible channel traffic is relayed. Regions express a routing policy. Radio signals can cross a region boundary, and region membership does not grant privacy.

Post offices and offline delivery

When a direct delivery remains unacknowledged, a host can deposit a sealed copy. A recipient can come back on another link or through another gateway, and the host there can try to obtain and hand over a copy. This is useful when a radio is outside coverage, its client is disconnected, or a route is temporarily unavailable.

Watch a message wait and arrive

SenderPost officeReplica hostsRecipient

  1. The sender tries direct delivery and waits for a receipt.
  2. After the deposit delay, a reachable host can accept the sealed message for later delivery.
  3. The backbone can keep copies at eligible replica hosts selected from the recipient’s address.
  4. A gateway that hears the returning recipient can fetch eligible copies and attempt delivery.
  5. The recipient gets the message, and the sender may see a delivery receipt. Other replicas age out under the current working-copy rules.

Retention, replicas and receipts

Managed networks can repeat --mail-replica-id <node address> to select from approved host identities. Posting and retrieval hosts need a shared policy, and remote replica requests in this mode require mutual DHT authentication. The local post office can still keep a local copy.

The standard host rule sets a deposit delay of 45 seconds, a limit of 100 text items per recipient, and a retention period of seven days for stored text. Current host defaults limit ordinary text storage to 200 MB, and fetched relay mail has an additional ceiling. Hosts attempt replication according to availability and advertised capacity. A stored status reports acceptance by a host or replica. The number of surviving copies depends on operational conditions.

Replica selection uses rendezvous hashing: rank eligible post-office IDs using the recipient’s address and select up to three positions. On reconnect, presence signals and sync can trigger a lookup or delivery. The sending and receiving hosts may use different links. A delivery acknowledgement originated by a reachable node and the eventual expiry of replicated ciphertext are distinct events.

Carry, flash storage and file mail

Carry allows mobile relays to move messages across disconnected parts of the mesh without first finding an end-to-end route. A host post office keeps sealed text on disk. Some firmware can keep a small local flash mailbox. File mail is a separate host subsystem with separate per-recipient and total capacity. Choose based on the content and path available.

Trust boundary. The current work rejects legacy unsigned remote deletion. Authenticated recipient fetch and replacement remote receipts are unfinished. A post office can still observe addressing, timings and ciphertext size, and can delay, discard or retain encrypted copies. The static sealed text path has no forward secrecy against later compromise of the recipient’s long-term key.

Pages, notice boards and public alerts

Browse and publish maarse:// pages

Use the page browser in a compatible client. Enter a maarse:// address with the serving node’s address and page path. A host can serve small pages from its pages directory. pages/index.mu is the root page, and pages/about.mu can be reached at /about. The client renders supported markup, links and images. It does not execute the remote page as browser HTML or JavaScript.

Keep pages compact for LoRa. Use compressed text and small images suited to the selected link. The host also supports page locks and notice-board functions. Their access rules are managed by the serving host. See the project guide and client capability before sharing sensitive material there.

Trusted alerts and signed bulletins

Public alerts use issuer keys and certificates scoped by trusted roots. Recipient policy checks signature, scope, validity and replay information. An issuer can publish updates or cancellation where authorized. Exercise and test states help clients distinguish practice traffic. Ordinary channel messages do not carry this alert authority.

Operators must provision trust roots and issuer policy before field use. Receiver software must support the alert data and presentation. Signed bulletins are a related mechanism with their own verification path. Neither a public alert nor a bulletin provides confidential group messaging.

Identity, linked devices and recovery

Node identity and safety numbers

A node address is derived from the public identity. It changes when a different identity is imported or generated. Display names help recognition, and safety numbers help verify that the keys at both ends match. Compare the number or QR code with the other person through a trusted channel before relying on the identity for sensitive communication.

One account on several devices

A person account groups host-backed devices with their own keys. The master authorizes a new device with a signed certificate and device list. Start linking on the new device, then approve it on the master by address or QR and compare the check words. The host, web client and Android app implement account features. A standalone radio can carry packets as a modem for a host-backed device.

Devices share received and sent copies through sibling synchronization. The recipient’s most recent announcements can influence which device gets the direct attempt. Offline person mail may be held under the person address and encrypted to the account’s weekly inbox key. Device removal updates the signed list, starts a new inbox chain for remaining siblings, and can take time to propagate to devices that are currently offline.

Radio hardware and firmware

Firmware protects state-changing radio administration across reboot using flash-backed counter reservations. Immediately after a reboot, a legitimate remote administrator may need to wait for the previous counter range to pass. The radio rejects a change if it cannot persist its reservation. Local companion access still uses USB or Bluetooth.

Choose the firmware image for the board you actually have. The two ESP32-S3 targets support Wi-Fi backbone operation. The nRF52840 targets use USB or Bluetooth for companion access. The host can run without radio hardware and exchange packets with other hosts over the backbone.

Flash and verify a radio

  1. Read the board marking, confirm the radio and antenna band, and choose the matching firmware artifact.
  2. Use a USB data cable. Enter the board's flash or UF2 mode as required. The host serves a browser flasher at /flash.html. Chrome and Edge are the browsers named in the project guide for that workflow.
  3. For a local build, use the board identifier with one of the commands below. For Windows native builds, install the toolchain dependencies for that board first.
  4. Connect to the resulting node over the available companion link. Read its version and node address, check the radio settings, and send a short message to a nearby node configured for the same radio.
# Linux, from the project root
./scripts/build-firmware.sh heltec-v4 flash /dev/ttyACM0

# Windows PowerShell, from the project root
.\scripts\build-firmware.ps1 xiao-nrf52840 -Flash

Radio settings, regulatory limits and power

Nodes must share frequency, bandwidth, spreading factor and coding rate to hear each other on a given LoRa network. Transmit power and duty budget determine when and how strongly a node transmits. Choose them for your region, board, antenna and permitted operating conditions. The radio's configured output and effective radiated power can differ because of an amplifier, cable and antenna. Verify the applicable rules for the band before transmitting. The firmware uses its duty scheduler to defer transmissions when airtime runs out, so a working link can still take time to deliver.

Lower spreading factors use shorter airtime. Higher spreading factors can help weak links at a substantial airtime cost. Start with two nearby nodes and known-good settings. Change one parameter at a time and record it in range tests. Firmware with a voltage reading also adapts routing effort as battery energy falls. A voltage reading is useful as a trend and requires calibration for precise state-of-charge or power measurements.

Run a host or server

maarse-host runs a software node, can serve the web client, and can connect to a radio modem. Choose it for a desktop user, a local gateway, or a radio installation with a computer. maarse-server uses the same host core with backbone defaults and an admin dashboard. Choose it for an always-on deployment that should accept configured backbone peers, keep post-office copies or relay for nodes behind NAT.

Local host setup

# From the repository root, Linux
./scripts/start-host.sh

# From the repository root, Windows
scripts\start-host.bat

# Example: a locally accessible host with a USB LoRa modem
maarse-host --data ./maarse-data --http 127.0.0.1:8080 --listen off --serial /dev/ttyACM0

Open http://127.0.0.1:8080/ on the host machine. For Windows use the radio's COM port, such as COM3, in place of /dev/ttyACM0. If a modem never appears, verify its firmware mode, data cable, serial access and baud rate. Confirm from the Devices list that the modem link is up. A companion connection to a standalone radio controls that radio's own node. A radio in modem mode instead transmits packets for the host node and takes its routing decisions from the host.

Dedicated server deployment

  1. Use a persistent data directory and run one instance per identity and set of listening ports. On Debian/Ubuntu the repository provides scripts/install-server.sh for interactive service setup. Windows host service packaging and tray controls are described in the technical guide.
  2. Set the backbone listener explicitly and restrict reachability according to the network you run. Use --public-addr to advertise a reachable DHT gateway endpoint. Add intended peers or DHT seeds. Advertise the address that clients can actually reach, including its port.
  3. Keep the web listener on loopback when publishing it through a reverse proxy. Use --require-key so local proxy traffic is checked too. Store the host access key separately from the dashboard admin password. When a local client uses a hostname other than localhost, use the access key. The initial admin password is kept in the data directory rather than printed in logs. Changing it ends existing dashboard sessions.
  4. For Internet-facing administration, terminate HTTPS at a reverse proxy. The installer includes a Caddy recipe for Let’s Encrypt, forwarding HTTP and WebSocket to the loopback listener and adding Secure to admin cookies. Set up the DNS name and certificate on the actual server. Restrict the raw backbone listener independently.
  5. Check service status, logs, dashboard, connected links and a bidirectional test message before making the endpoint available to others.
# Example arguments for a privately managed server behind a web proxy
maarse-server --data /var/lib/maarse-server \
  --http 127.0.0.1:8080 --require-key \
  --listen 192.168.1.20:4242 --public-addr 192.168.1.20:4242

This example uses a private IP. Configure the endpoint explicitly on the peers that need to contact it. The running binary's --help, service arguments and effective dashboard settings should guide deployment. The installer identifies the service configuration file and data directory. Use the project's platform instructions when migrating an existing service.

Data, authentication and updates

The data directory holds the node identity, settings, and optional history, account state, logs and post-office files. An identity backup and a disk copy of message history serve different purposes. Keep private identity material, access keys and admin password files out of logs and shared archives. The browser and Android client use headers for web credentials in the reviewed implementation. Query-string keys are disabled by default. Operators may temporarily enable the legacy client path with --allow-legacy-web-token on a trusted network. Use HTTPS/WSS when a client crosses an untrusted network.

New admin passwords use Argon2id in the reviewed code. Existing password records are readable during migration and acquire the new format when the password is reset. Use the installer or the documented admin-password procedure. Treat the dashboard login and companion API access as separate credentials.

Use signed releases and verify the correct board and version before applying an OTA update. Firmware checks the manifest, board identifier, image hash and signature before activation. For a remote update, the radio must authorize the administrator and accept the newer version. The reviewed firmware disables OTA without a usable configured release key and refuses the public development key. Release CI validates the public key and checks any configured private signing key against it before building. Device behavior for a particular binary depends on its build settings. USB recovery depends on the board bootloader and remains an important maintenance route.

Links, backbone and gateway discovery

A mesh can combine inexpensive handheld radios, fixed repeaters and better-connected hosts. LoRa carries packets where compatible radios can hear one another. A host-to-host TCP or UDP link can move packets between areas, and a radio modem can give a host local coverage. The choice of link changes airtime, file limits and failure modes.

The board has its own node identity and routing state. It peers with a host and can continue local mesh operation when the Internet link goes away.
Wi-Fi LoRa modem mode
The host owns routing and identity for traffic using the radio. Configure a modem passphrase on both ends where required. Some setups have the host dial a listening modem with --modem-ip. The firmware can fall back to its saved standalone node role after a prolonged outage and return to modem operation when the host reconnects.

Backbone DHT

The TCP listener defaults to loopback. Set --listen <bind address>:4242 to accept traffic from another machine, including incoming modem sessions on the same listener. For a private backbone, choose an authenticated VPN interface and list your peers or seeds there.

New hosts prefer the D7 D9 exchange. Both sides use fresh challenges and sign the corresponding request or response. The request signature identifies the calling host. Ownership of a destination mailbox is a separate check. Configured endpoints can fall back to older exchanges for migration; newly discovered endpoints require the modern exchange. DHT traffic and ordinary backbone packets still require transport encryption on untrusted links.

Watch a host discover a gateway

ClientLocal hostDHT peerGateway

  1. The client addresses a message to a node the host has not heard.
  2. The local host starts a lookup among known contacts and configured seeds.
  3. A peer returns a route claim and the destination announcement. Modern exchanges can authenticate the DHT responder separately from the gateway signer.
  4. The host validates the evidence and applies endpoint and compatibility policy.
  5. An eligible gateway can be connected for ordinary packet forwarding. Reachability is confirmed by actual delivery.

The distributed hash table, or DHT, is the hosts' shared directory. A route record says which gateway claims it can reach a particular node and where that gateway can be contacted. A host looks up a previously unknown destination, learns a candidate gateway, and tries to establish a packet link to deliver the waiting message. The post office also uses the list of known hosts to select candidate replica holders.

A route record includes the destination's signed announcement. A modern record also has a gateway signature over the endpoint, hop count, issue time and announcement. The request/reply handshake and the gateway record prove different things. The handshake proves control of the connected DHT identities, while the gateway signer may be a different host. An authenticated claim can still give an inaccurate estimate of actual reachability. Legacy fallback on operator-configured endpoints may lack either proof.

The working-copy hardening retains the address of an existing contact when a discovered record proposes a different one. Automatically discovered endpoints must resolve to eligible public addresses before the host attempts to dial them. Configure private hosts with --peer or --dht, or use --dht-allow-private <host:port> for a private endpoint that should remain discoverable without becoming a bootstrap seed. A stable hostname can keep the endpoint string constant through a public IP change. Explicitly reconfigure a changed endpoint when the old one should be retired.

The current design is Kademlia-like. It compares 16-byte addresses using XOR distance, refreshes published records periodically and expires stale entries. Hosts replicate records more broadly in small networks. Route discovery, message delivery and confidentiality are different steps. A lookup can succeed while the subsequent link or message still fails. A returned route can affect reachability and expose metadata to the chosen gateway even when the message payload stays encrypted.

How the network works

Host announce freshness. The host saves the latest accepted dated timestamp per identity and rejects older statements after restart. Its accepted window extends from seven days in the past to ten minutes in the future. Clockless announcements are accepted while no recent dated statement is known, and equal timestamps can still recur. This check also applies when a host learns an announcement through the DHT.

Node roles

Client
A regular endpoint that uses existing forwarding infrastructure. This reduces duplicate traffic where repeaters are already available.
Repeater
Fixed or deliberately placed infrastructure that forwards eligible traffic and participates in path discovery. A repeater role alone does not turn a radio into a full host post office.
Relay
A limited forwarding node for handheld groups without infrastructure. It can carry copies of otherwise undeliverable messages until it meets another node.
Anchor
Infrastructure that can participate in longer routes by splitting them into segments.
Auto
A firmware role that uses observed repeater coverage to decide when a handheld should relay. A node near the edge can temporarily bridge covered and uncovered neighbours. Stabilisation timers prevent immediate role changes whenever signal conditions fluctuate.

From first packet to delivery

  1. Identify the recipient. A node address identifies its public keys. An announcement attributes its contents to that node and may carry its display name, role, position or capabilities. The project distinguishes a full address from a shorter path ID, which exists to save bytes in forwarding headers.
  2. Discover a path if needed. A limited path request propagates until there is a route to the target. The request can carry the first encrypted direct message. Repeaters suppress eligible duplicate floods. Nodes apply a proof-of-work stamp to selected packet types as a traffic cost.
  3. Send along the path. Later packets can use the discovered route instead of repeating discovery. Per-hop forwarding and retry logic handle local reception problems. The destination's acknowledgement indicates network delivery and has a different purpose from a per-hop forwarding signal or a human read receipt.
  4. Recover when the path breaks. The router can remove a stale route, try local repair around an unavailable hop, or start a fresh request. Some roles and offline paths can carry or store the message instead of expecting immediate delivery.

The radio scheduler prioritises time-sensitive acknowledgements and responses ahead of bulk fragments and background announcements. It spaces work using settings such as spreading factor and airtime budget. Ten nodes sending on the same channel share that resource. A successful short message is a better initial connectivity test than a burst of large files.

Carry, post offices and file mailboxes

  • Carry temporarily spreads a bounded number of encrypted copies among eligible relay encounters. The copy lifetime is short. A delivery notice can stop further carrying.
  • Post office stores encrypted text for people or nodes that are offline. Host replicas can improve availability, subject to topology, quota and expiry. The reviewed host refuses legacy unauthenticated remote deletion requests. Other copies may stay until their configured lifetime expires. Full recipient-authenticated fetching and deletion are still protocol work.
  • File mailbox is a separate sender-host disk feature. A file can wait for the recipient to reappear, subject to the route limit, disk quotas and expiry. A file too large for the eventual LoRa route waits for a suitable route. Radio flash and a host file mailbox have different capacity and durability.

TLS and firmware signaturesHTTPS/WSS protects the client-to-proxy web hop. Firmware signatures authenticate an update to an embedded release key.They govern different trust relationships. Neither supplies authenticated public DHT federation for raw backbone peers.

Verify a contact's safety number or QR with the person through a trusted channel when establishing identity matters. Treat password files, device data directories, recovery phrases and account backup codes as private credentials. Consider which observable metadata your use case can tolerate even when the message contents are encrypted.

Wire protocol and integration

The radio packet format defines packet types, addresses, paths, payload bounds and deduplication. The companion protocol uses length-prefixed command and event records over USB, Bluetooth or WebSocket. A UI should expose a feature only when the attached host or board supports the command and capabilities. The TCP packet backbone carries the mesh packets in length-prefixed frames, while DHT RPC has its own message set on the same listener. Use the repository protocol tables for byte order, type IDs, command availability and version handling. Prefer the parser, encoder and compatibility tests when the prose disagrees with current code.

OTA packages include board identity, version, image size, hash and signature. Staging limits and local/remote apply policy differ by board and firmware configuration. Transport and authorization must be validated separately from the image’s signature. Use a version-matched image for every board in a rollout and check the device after restart.

Diagnostics, telemetry and integrations

Start with the link closest to the user. The host's Devices list describes active packet and modem links, last activity, counters and supported modem readings. The node Status view describes its identity, role, battery, radio configuration and routing counters. The server dashboard adds network-wide observations from the vantage point of that host.

Simulate, test and measure

The Denmark simulator is an interactive way to explore routing, coverage, mobility, backbones, offline delivery and outages. Start with the same scenario for each comparison. Inspect routes, traffic, airtime and delivery events before changing one variable, such as repeater placement, an outage, spreading factor or node movement. Keep the scenario parameters and random seed when comparing outcomes.

In the working copy of the browser simulator, open Traffic to filter recent packets, pin a recorded path, or scrub the simulated timeline. The retained range is shown beside the slider. Select an outage from Scenario events and choose Live to return to the current run. The Great Belt traffic demo ships with a fixed seed and is designed for terrain disabled. Verification ladder

  1. Component tests verify packet codecs, protocol handling, cryptography and routing logic.
  2. Local integration tests exercise clients, packet links and host interactions. The DHT integration scenario uses five local hosts and explicit permissions for private gateways to verify delivery and a return acknowledgement.
  3. Board builds establish whether a specific firmware target compiles with the selected options.
  4. Field measurements validate antenna, radio, battery, congestion and regional configuration. Use the field-test guide to record both successes and failures, including packets seen, ACKs, SNR, elapsed time and power.
  5. Release validation confirms an exact version, distribution artifact, update workflow and compatibility with deployed peers.

The CLI simulator can produce an event trace for later analysis. The test lab adds repeatable experiment tooling. Record which environment produced every result so an operator can distinguish a build result from a physical or production observation.

Glossary and source materials

Announce
A signed statement about a node and information it chooses to advertise.
ACK
An acknowledgement. Link or hop ACKs support delivery along the route. An end-to-end receipt reports that the receiving node got the message.
Companion
A client interface to a node over an appropriate link. The companion commands and events are distinct from transmitted radio packets.
DHT
A distributed lookup table that helps hosts find gateways and other backbone contacts.
Gateway
A host that provides reachability between links or to nodes behind it.
Post office
A node or host that stores sealed messages for later handover.
Receipt
Evidence of delivery at the relevant protocol layer. A storage confirmation and a recipient delivery receipt establish different events.
RSSI and SNR
Measurements of received signal strength and signal relative to noise.
Trunk
A link between hosts or network segments. A directional LoRa trunk can provide a low-bandwidth backup path.

Use the technical guide for installation and configuration detail, the protocol specification for wire layouts and command tables, and the field-test guide for evidence collection. Links to the public repository can differ from this working-copy snapshot.
