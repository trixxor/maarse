Architecture

Nodes, hosts and clients, the layers they share, and the code behind them.

TL;DR

What: three kinds of part. A node sends, receives and sometimes forwards packets. A host is a program that is a node itself and also a gateway between radios, the internet backbone and clients. A client is the app or web page you look at.

Why it is built this way: the protocol core is written once, in Rust, without a heap, so the same code runs on a small radio, on a PC and in the simulator. That is why simulator results say something about the real router.

Advantages

  • One router for radio, host and simulator
  • A phone or PC can be a full node and a gateway
  • Clients are thin: they talk one companion protocol

Good to know

  • The radios have almost no memory to spare, so every addition is checked
  • The Android app and web client must be kept level by hand
  • Many crates: more to learn than a single program

The three parts

PartWhat it isRuns on
NodeAn identity that sends, receives and, depending on its role, forwards packets.Firmware on a LoRa board; the host program; the phone app, which embeds the host
HostA node that is also a gateway. It attaches radios (USB, Bluetooth, Wi-Fi modem, KISS), joins TCP and UDP links, keeps history and a post office, and serves the web client.PC, server, phone
ClientThe user interface. It talks to a host or to a single radio with the companion protocol.Browser, phone

The layers

 UI              web client · Android app · Heltec display
 ─────────────── companion protocol (USB serial, Bluetooth, WebSocket) ───────────
 Application     direct messages · channels · files · voice · pages · alerts · sensors
 Security        identity · static seal · ratchet · channel keys · signed bulletins
 Routing         path discovery · source routing · per-hop ack · carry · post offices
 Link            LoRa (SX1262) · TCP backbone · UDP · serial · KISS · Wi-Fi modem

Each layer only uses the one below it. The link layer does not know what a message is, and the routing layer does not know what is inside one.

Roles

A node's role decides whether it forwards for others. Each role has its own page: client, relay, repeater, anchor, host and server, and a lab on roles and devices lets you try them.

RoleForwards for others?Typical device
ClientNoPhone, handheld
RepeaterYesRooftop or hilltop board
RelayYes, but only for up to 4 hops, and it waits longer so real repeaters win (the "forest mode")Handheld in the field
AnchorYes, and it splits long routes so a route may be 12 hops on each side of the backboneA host or server that is always online

A node low on battery forwards less, and at the critical level it forwards nothing.

Where the code lives

  • Shared cratesProtocol core, crypto, host rules, voice, firmware packaging.
  • Host sideThe host, web client, Windows service and the Android app.
  • FirmwareESP32-S3 and nRF52840 boards.
  • Simulation and testsSimulator, fuzzing, the test lab.

Shared crates

CrateResponsibility
maarse-coreProtocol core, no_std, no heap: addresses, packet format, duplicate filter, route table, airtime budget, the Router, send priorities, announce stamps and the companion protocol codec. No dependencies.
maarse-cryptoIdentities, signed announces, the static seal, the ratchet, channel keys, signed bulletins, firmware signing and the recovery phrase.
maarse-hostrulesThe host's pure rules, with no I/O and no clock, shared by the real host and the simulator so both run the same decisions.
maarse-voiceVoice messages with Codec2.
maarse-uf2ELF to UF2 conversion, and maarse-sign for signed firmware and releases.

Host side

Crate / directoryResponsibility
maarse-hostThe host as a library (also embedded in the Android app) and two programs: maarse-host for desktops and maarse-server, a dedicated server with an admin dashboard. It owns the web server, WebSocket, history, post office, DHT, MeshCore access, page server, MQTT and firmware updates.
maarse-clientThe web client (static HTML and JavaScript, also a PWA) and flash.html, the browser flasher. Served by the host.
maarse-service, maarse-tray, maarse-desktopThe Windows service with signed updates, the tray app, and the installed desktop app (maarse.exe).
maarse-androidThe JNI bridge that runs maarse-host inside the Android app.
android/The native Android app in Kotlin and Jetpack Compose, which talks to the embedded host over the companion protocol on loopback.

Firmware

DirectoryResponsibility
firmware/commonShared firmware logic: node, bus, storage, OTA.
firmware/nrfnRF52840 with SX1262: WisMesh Tag and XIAO nRF52840. Bluetooth, USB serial, UF2 bootloader.
firmware/espESP32-S3 with SX1262: Heltec V4 and XIAO ESP32-S3. Bluetooth, Wi-Fi, display, USB.

The ESP32 stack is tight

With a host attached, the Heltec firmware has under 100 bytes of stack to spare. After adding a static or a deeper call, check the stack with tools/stack_probe.py before flashing.

Simulation, testing and measurement

Crate / directoryResponsibility
maarse-simA command-line simulator running the real Router in many virtual nodes.
maarse-sim-wasmThe same engine compiled to WebAssembly for the Denmark simulator.
maarse-fuzzA small dependency-free fuzz engine, deterministic and reproducible by seed.
maarse-lab, maarse-lab-dataA test lab in the browser: suites, fuzzing, simulator scenarios and benchmarks, with history.
tools/End-to-end and hardware tests (Python and Node), release tooling, asset generators and simulator experiments.

Dependencies: maarse-core and maarse-crypto depend on nothing in the project. maarse-hostrules, the host, the firmware and the simulator all build on them. The simulator and the firmware share maarse-core, which is why a simulated result runs the same router code as a radio.
