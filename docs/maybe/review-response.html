Response to the external reviews

Covers chatgpt.md (strategic analysis) and gemini.md (a critique of that analysis). Each claim was checked against the code and docs (README, GUIDE.md, maarse-crypto/src/ratchet.rs, backlog). 15 November 2026.

Short version. Both reviews get the big picture right: Må:rse is broad, untested in the field and has no outside crypto review, and those three gaps matter more than any new feature. ChatGPT worked from the README alone. Several of its "improvements" already exist (hop ACKs, fragmentation with NACK, resumable transfers, duty-cycle enforcement, spam stamps, regions). The rest of its list is a roadmap for a national product, not for a two-radio prototype. Gemini is sharper and finds two real weak spots: route repair always goes back to the sender, and the ratchet's skip window is too small for carry and mailbox delays. Two of its fixes go too far, though. Replacing path routing entirely and turning every radio into a dumb modem would take away what Må:rse does best: standalone repeaters that route on their own, without a host.

1. ChatGPT review

Where it is right

  • Proof before features. Its P0 list (field measurement, crypto review, failure tests, 72 h run) matches our own backlog. All the numbers we publish so far come from the simulator.
  • Treat the backbone as an optimisation, not a dependency. This already holds for local traffic, because LoRa routing never needs TCP. What we lack is a defined behaviour when the backbone splits and later heals.
  • Traffic priorities. Agreed. This is our load control todo (queue priorities and flood slots per SF). It has been rated low priority, and that rating should go up.
  • Signed bulletins. Offline-verifiable signed broadcasts from a trusted key are a good, cheap idea that fits the existing announce and channel machinery.
  • Metadata. It is correct that the recipient and the route are visible on air. We already document this; we should state the limit plainly and leave it at that.
  • Regulatory check of 869.525 MHz, ERP and duty cycle before any wider rollout, and the "supplement, not replacement for authority radio" positioning.

Where it is wrong or outdated

Claim / suggestionReality in the code
Add hop ACKs with small ACK packets, backoff and jitterAlready there: per-hop ACKs with retransmission, end-to-end ACK, and SNR- and battery-weighted flood delays.
Add fragmentation, selective retransmit, resumeFragmentation with NACK of missing pieces exists. Firmware transfers resume per 4 KB block, even across restarts.
Prevent spam and fake trafficProof-of-work stamps on announces and path requests. Regions keep local chats local.
Carry must not delete before an ACKDone: CarryAcked and "delivered (carried)". The only open point is turning carry on for the relay role in firmware.
Wi-Fi node must keep working when the host goes awayAlready true in mesh node mode. Modem mode is the deliberate dumb variant.
Scores (9/10 "potential")Flattering but not meaningful. The only honest score in its table is maturity: 3.

Over-scoped for now

QUIC, iOS, a mobility score with speed and heading, adaptive SF per link, dual-radio vehicles, a six-level national hierarchy, 10,000 nodes, Merkle-tree partition sync. Each is defensible on its own. Taken together, they would multiply the complexity it warns about in the same document. Adaptive SF per link is especially costly in LoRa: both ends must share the SF, so it needs a rendezvous profile and negotiation. Today a host with two modems already bridges areas that use different SF.

2. Gemini review

PointVerdictComment
A. Feature creep: cut voice and web pages from the corePartlyThe risk is real. But the premise is off: there are no live voice calls over LoRa. LoRa carries short Codec2 messages, and Opus calls run only over TCP. These features sit above the router and cost nothing on the air unless they are used. Our response is to keep them, but put them behind the priority queue as the lowest class, and leave them out of the security review scope for v1.
B. Replace path routing with gradient routingProblem yes, fix noValid finding: repair is end-to-end. With no ACK within 20 s, the route is dropped and the sender floods a new path request. On a long route that is slow and expensive. But gradient routing needs proactive per-destination cost tables everywhere, which means periodic announces, the kind of airtime that MeshCore-style path routing avoids. Better fix: local repair. The hop that loses its next neighbour tries a small, scoped path request (TTL 2–3) to the rest of the route, or a known alternative neighbour, before giving up to the sender.
C. DHT → gossip/CRDT catalogue between gatewaysMostly agreeWe use Kademlia-style XOR, K=8, α=3. With 20–50 hosts, a full replicated, signed, TTL'd reachability table is simpler and survives splits better: each side keeps a full copy and merges on reconnect. Keep the DHT code for large scale. Make "full table when small" the default and measure it in dht_test.py.
D. Ratchet goes out of sync with loss and delay; use ECIES per messageHalf rightThe proposed ECIES/sealed-box format already exists: it is our static format, and the ratchet falls back to it. Loss and reordering are handled with n/pn and a skip window. The real weakness: MAX_SKIP = 8, and a message that arrives after the window can never be opened. Carry and mailbox can easily deliver a message hours late, after more than 8 newer ones. Fix: send carry and mailbox traffic in the static format (or as a new init), raise the window on the host, and show "could not decrypt" to the user instead of dropping silently.
E. Radio as dumb modem (RNode model)Disagree as defaultWe already support this: serial modem and Wi-Fi modem mode. Making it the only model would mean every solar repeater on a mast needs a Pi, which works against low power and against "no single host required". Keep both. Routing in firmware stays, because maarse-core is shared no_std code that the host and the sim run too, so a protocol fix is one code change and a reflash.

Gemini's agreement points (hybrid is right for Denmark, role separation, priorities under the 10 % duty cycle, carry between islands) match our design and need no comment.

3. What we should actually do

Ordered by value for effort. Items that are already on the backlog are marked.

  1. Field measurement with range-test mode (backlog). Without it, every comparison in the README stays unproven.
  2. Send-queue priorities and flood slot following SF (load-control todo, raise from low). Order: ACKs and path replies → emergency/high → direct → channel → files and voice chunks; file transfers can be interrupted between fragments.
  3. Ratchet and delay fix: use the static format for carried and mailbox messages, use a larger skip window on the host, and show decrypt failures to the user. Small change, closes a real loss path.
  4. Local route repair at the failing hop before falling back to the sender. Measure it in maarse-sim on the E45 and hill scenarios.
  5. Turn on carry 4 for the relay role in firmware (decision pending; the sim says +14–16 points for about +10 % airtime).
  6. Backbone split behaviour: a replicated, signed reachability table between hosts with TTLs, and on reconnect, exchange of mailbox message IDs (a simple ID list is enough at our scale; Merkle trees can wait).
  7. Signed bulletins: a channel type whose messages must carry a signature from a configured key, verified offline, with higher priority.
  8. Fault-injection test runs: 72 h soak with repeaters switched off and backbone links cut, using the hardware we have.
  9. External crypto review of the ratchet, replay handling and firmware signing. Do this after point 3, so the reviewers see the final design.

Deliberately not now

QUIC, iOS, adaptive SF per link, mobility scoring, dual-radio vehicles, national hierarchy and node classes, full partition-recovery protocol, replacing path routing, and dumb-modem-only firmware. Revisit after field data exists. The long-range anchor and custody idea stays parked as before.
