Features · Explanation

Messages

How a private message is protected, delivered and paid for in airtime.

TL;DR

What: A direct message is a private, end-to-end encrypted text from one person to another, with a delivered mark when the other side has decrypted it. It travels along a route through repeaters or over the internet, and waits in a post office if the recipient is away.

Why: Radio is public: anyone in range hears every packet. The message must be unreadable to everyone but the recipient, must hide who sent it, and must still be small enough to cost little airtime.

Strengths

  • Encrypted end to end, with the sender hidden inside the message
  • Forward secrecy between contacts that support it: a leaked key does not open old messages
  • A delivered mark that means "the other node decrypted it"
  • Short texts are compressed to about 56 % of their size
  • Most messages in a conversation use a compact form with 22 bytes of overhead instead of 69

Good to know

  • MeshCore's frame is lighter, because it pays 2 bytes for authentication where Må:rse pays 16
  • A text is at most about 140 bytes over LoRa: this is for short messages, not documents
  • The ratchet is a draft and has not been reviewed from outside
  • Mail waiting in a post office is sealed without forward secrecy

What a message costs

A short text is mostly overhead. The text of a 40-byte message is less than a third of the 135 bytes that go on the air with the old frame. The compact frame, which is on by default between nodes that both announce support for it, cuts it to 88 bytes. MeshCore's documented frame is 57 bytes.

This is a trade-off, not a flaw in either design. Only the destination address and the acknowledgement token could be made shorter without weakening security, and that would need an outside review first.

Compression

Short chat messages are compressed with a codebook of common Danish and English words, to about 56 % of their size. This is used only toward nodes whose announce says they can read it.

The formats

Source: maarse-crypto/src/seal.rs, ratchet.rs, spec section 6.2 and 6.3.

Static seal (no session)

e_pub (32) | sender address XOR k1 (16) | ChaCha20-Poly1305(k2, message) | tag (16)

Overhead 64 bytes, so the largest message is 212 − 64 = 148 bytes. Used for the first message to a stranger, and for everything that goes into a post office.

Ratchet frame

type (1) | ratchet key (32) | sender XOR mask (16) | n (u16) | pn (u16)
  | ChaCha20-Poly1305(mk, message, AAD = these 53 header bytes) | tag (16)

Type 0xF0 is the first message of a session, 0xF1 a ratchet step. Overhead 69 bytes; the largest text is 143 bytes.

Compact frame working copy

type 0xF2 (1) | session id (3) | n (u16)
  | ChaCha20-Poly1305(message key, message, AAD = these 6 bytes) | tag (16)

Overhead 22 bytes. The tag is the full 16 bytes and the key is new for every message. After a ratchet step, the first 2 messages carry the full ratchet key so one lost message does not break the chain. A sender takes its next step after at most 8 messages on the current key.

Measured in tests, average encryption overhead: 29.7 bytes for mixed chat, 33.6 bytes for strictly alternating messages, compared with 69 for the long form. In tests with 20 % loss, three tries and up to 20 % swapped order, 0.1 % of messages became unreadable (the long form: 0 %).

Why the simulator now uses honest sizes

The simulator used to count a 40-byte text as 60 bytes in total, without the encryption overhead, and a preamble of 8 symbols where the firmware uses 16. With honest sizes, the E45 car scenario went from 954 s and 97 % to 2 426 s and 81 % (that run, in the report, section 6.1). The compact frame brought most of that back: −30 % airtime and +10 points delivered in the car, −17 % in the forest. simulated See simulation results.
