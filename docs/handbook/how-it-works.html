Understand · Explanation

How messages travel

Find the route once, confirm every hop, and treat radio and internet as one network.

TL;DR

What: the sender floods one small path request. Repeaters add themselves to it, the recipient picks the best of the routes it heard, and later messages follow that route. Every hop confirms the handover. Over the internet, a host looks the recipient up in a shared table and sends straight to the right area.

Why: a flood makes every node transmit for every message. A route makes only the nodes on it transmit, which saves the scarce resource of a LoRa mesh: airtime.

Advantages

  • Only a few nodes transmit per message
  • A lost packet is resent on the hop where it was lost
  • A broken repeater is noticed at once
  • Far-away areas stay quiet: only the recipient's area is woken

Good to know

  • The first message to a new destination is slower (route discovery)
  • Routes can go stale when a node moves
  • A route is at most 12 hops without anchors
  • The internet part needs at least one connected host

1. Find the route once, then follow it

Try it: flood against route

Fifteen nodes between a sender S and a receiver R. Press the buttons in order and watch the airtime add up.

Flooding costs the same every time, because every node repeats every message. A route costs more for the first message, because a path request is flooded first, and much less for every message after it. In this layout the route has paid for itself after about three messages.

Airtimes are computed with the project's formula (maarse-core/src/airtime.rs) at SF9, 125 kHz, coding rate 4/5, preamble 16, for a 22-byte text message. The 15-node layout is an illustration, not a measurement.

A flood makes every node that hears a message repeat it. It is simple and robust, but each message costs airtime on every node, and in a busy area the copies start colliding.

Må:rse floods only a small path request. Every repeater it passes adds itself to it. The recipient waits briefly to collect several copies and picks the best one, not simply the first to arrive: it avoids a route whose last hop is weak, then prefers fewer hops, then a stronger signal. It sends that route back, and from then on messages follow the route.

If the sender has a message queued, it rides inside the first path request, so the first message is not delayed by the discovery.

2. Confirm every hop, not just the end

Press Lose a packet on hop 3 in the player above to see this happen.

On a long route some packets get lost: a truck drives past, or two radios talk at once. In Må:rse each node listens for the next node to pass the packet on, and takes that as the confirmation. If it does not hear it, it sends again. The recipient also sends an end-to-end acknowledgement, which is what shows as delivered in the app.

If even that does not arrive, the sender forgets the route and discovers a new one.

3. Radio and internet are one network

Try it: from one radio area to another

Three radio areas, each with a host, joined by the internet backbone.

The host looks the recipient up in a shared table and sends straight to the host that can reach them. Only the recipient's area is woken. The third area does not hear a thing.

Illustration of the design in spec section 8. The transmission counts are simplified to show the principle.

LoRa is slow but reaches kilometres without infrastructure. The internet is fast but only exists where there is a connection. In Må:rse both are just links. A host (a PC or Raspberry Pi running maarse-host) or an ESP32 board on Wi-Fi joins its radio area to the backbone.

To reach someone far away, the host looks the recipient up in a distributed hash table (DHT) and sends straight to the host near them. There is no central server, and only the recipient's area hears the traffic.

What each packet costs on the air

Every transmission occupies the channel for everybody in range. Even a bare acknowledgement costs a quarter of a second.

For short packets, the fixed cost (preamble and header) is a third to a half of the airtime. That is why Må:rse works so hard to send fewer packets, and not only smaller ones.

Computed with maarse-core/src/airtime.rs; packet sizes from the airtime report (docs/maybe/airtime-optimisation.md, section 1).

When something breaks

  • A packet is lost: the hop that sent it resends, up to four times.
  • A repeater is gone: the hop tries a local repair, and if that fails the sender discovers a new route.
  • The recipient is offline: a mailbox keeps the message; see mailboxes and carry.
  • The route is longer than 12 hops: an anchor repeater splits it into legs, each up to 12 hops.

Path discovery step by step

Source: maarse-core/src/router.rs, spec section 5.2. working copy

  1. The sender floods a PathRequest with an empty path. The payload is a random 16-byte reply token, optionally the first queued Data payload, and a small proof-of-work stamp. The message is included only if 16 + len + 5 ≤ 212.
  2. Each forwarder that may forward appends its own path ID, increments hops and re-floods after a delay. A forwarder that is not an anchor drops a request whose path is already 12 long.
  3. The target delivers any included message at once, then waits 10 time slots to collect more copies and picks the best trail (see "Choosing the best route" below).
  4. The target sends a PathResponse to the reply token. Its header path is the reverse of the chosen trail and its payload is the forward path.
  5. The sender recognises the token, stores the forward path as the route, acknowledges any included message and sends the queue along the route.
ConstantValueMeaning
PATH_RETRY_MS20 000 msAn unanswered request is repeated with a new token
PATH_RETRIES2After the last retry, queued messages are dropped, or carried if carry is on

Choosing the best route

Among the copies heard during the wait, the target picks the trail with the smallest score, compared in this order: first avoid a weak last hop, then the fewest hops, then the best signal-to-noise ratio (SNR). Spec section 5.3.3.

How floods are spread out

A node that may forward a flood waits before sending: delay = bucket × slot + energy penalty. The bucket (0 to 7) grows with the SNR it heard the packet with. A near neighbour with a high SNR therefore waits longest, so distant forwarders go first and routes get fewer hops. A relay waits two extra slots so a real repeater wins. The slot is 200 ms by default, and the radio layer adds a random 0 to 1 slot.

Battery stateExtra wait
Full0 ms

Critical3 000 ms (and nothing is forwarded)

Suppression: if a node hears another strong copy of a flood it has scheduled, it cancels its own transmission. Weak copies do not count, because they come from far away and cover a different area. A node with at least 3 neighbours also passes on only 80 % of path requests; a node with fewer neighbours may be the only way through and forwards all of them.

simulated In maarse-sim the 80 % rule together with the 20 s retry changed airtime by −9 % (forest), −24 % (car), −4 % (town), −13 % (national) and −16 % (outage). Not yet tested on boards.

Source routing and the per-hop confirmation

Spec sections 5.4 to 5.7. working copy

For packets with a path, hops is the index of the next forwarder. A node whose path ID is at that index increments hops and retransmits after 50 ms (SOURCE_ROUTE_DELAY_MS).

The per-hop confirmation is implicit: after sending, the node listens for the same packet ID with a higher hops. No separate acknowledgement packet is sent for a hop, which saves airtime.

The end-to-end acknowledgement is addressed to a token made from the message ID, ack_token(id) = id | !id, so the acknowledgement does not name either party. The last hop has no implicit confirmation, so the end-to-end acknowledgement covers it.

Anchors: routes beyond 12 hops

Spec section 5.8. working copy simulated on a 210 km motorway.

An anchor is a fixed repeater that splits a long route into legs. When it receives a path request with a non-empty trail it remembers the reply token and the trail so far (for 120 s, at most 16 legs) and forwards the request with an empty trail. When the response comes back, it stores its own route to the target and sends the first leg to the sender. The sender's route therefore ends at the anchor, and the anchor continues along its own route. Several anchors in a row work the same way, up to 64 hops in total.

The backbone and the DHT

Source: maarse-host/src/links.rs and dht.rs, spec sections 8.2 and 8.3. working copy

A backbone link is a TCP connection carrying frames of length (u16, little endian, 1..255) | Må:rse packet. Packets that arrive over TCP are treated as heard with a good signal (SNR 10), so the router can use them like any link. Links use TCP keepalive, and outgoing peers are reconnected every 5 seconds.

The DHT is Kademlia-like, uses TCP only and never runs over LoRa. A node's ID is its Må:rse address and distance is XOR. To limit one machine filling the table with made-up identities, at most 4 contacts may come from the same IPv4 /24 or IPv6 /48. Contacts are saved to dht-contacts.txt and used as seeds at the next start.

The first two bytes of an incoming connection select the protocol: D7 D7 is a DHT request, 4D 4D ("MM") is an ESP32 LoRa modem over Wi-Fi, and anything else is the length of the first backbone frame.
