Alerting in Må:rse: what exists, what others do, and how to make it unforgeable

A research review of signed bulletins and area alerts, compared with cell broadcast (EU-Alert, S!RENEN, WEA, ETWS), IPAWS/CAP and mesh systems, with a threat model and ranked recommendations. Written 16 November 2026. No code was changed.

How to read the evidence marks. Verified means I read it in the repository (file and function named). Inferred means a conclusion drawn from the code that I did not run or test. External means a claim about another system, with a source link. Some external sources are secondary (news, Wikipedia); this is noted where it matters. Byte counts are from constants in the code. Airtime numbers come from the Semtech formula with the firmware defaults (RadioConfig::EU_DEFAULT: 125 kHz, CR 4/5, 16-symbol preamble, explicit header, CRC on).
Short version. Må:rse already has the hardest piece that cell broadcast never got: every bulletin carries an Ed25519 signature that any receiver can check offline. Cell broadcast alerts (EU-Alert, S!RENEN, WEA) are not authenticated end to end, and researchers have spoofed them with cheap radios. That is a real advantage.

Around that signature, though, almost everything else is missing. There is no replay protection (the signed timestamp is never checked), no expiry, no alert ID, no cancel, and no status flag to tell a real alert from a test or exercise. Trust is a flat list of keys typed on the command line, with no hierarchy, scope or revocation. The signing key is the node's everyday identity, and the host signs anything typed into the #bulletin chat with no confirmation. The "verified" mark is plain text in the message ([Verified bulletin] …), so anyone can type the same thing on another channel. Firmware, Android and the web client do not verify at all. Repeaters give #bulletin packets top priority without verifying them, so a forger gets the fast lane.

The fix fits LoRa. A compact alert v2 format (ID, expiry, status, event, severity, area and signature) leaves about 105–109 bytes of text in one 255-byte packet. Add a two-level key hierarchy with short-lived issuer certificates (about 156 bytes, sent once and cached), self-revocation, verify-before-prioritise on repeaters, and a two-person rule for the most severe alerts. Hawaii in 2018 shows that operator error is a bigger risk than crypto.

1. What exists today

1.1 Wire format Verified

Source: maarse-crypto/src/bulletin.rs, protocol spec section 6.6, GUIDE "Signed bulletins". A bulletin is an ordinary channel message on the hashtag channel #bulletin. Its key is derived from the name (hashtag_key), so the key is public and anyone can read or post. The decrypted plaintext is:

0xB1 | timestamp (u32 BE, Unix s) | Ed25519 signature (64) | text
signed: SHA-256("maarse/bulletin/v1" | channel address (16) | timestamp | text)
  • OVERHEAD = 69 bytes. The first byte, 0xB1, can never start valid UTF-8, so a bulletin is never confused with ordinary text.
  • Around it sit the channel seal (seal::CHANNEL_OVERHEAD = 40: 8-byte nonce, 16-byte sender address, 16-byte Poly1305 tag) and the packet header (FIXED_HEADER = 18, plus 2 with a region). With MAX_PACKET = 255 (maarse-core/src/lib.rs), that leaves 128 bytes of text, or 126 with a region.
  • The signature covers the channel address (good: domain separation), the timestamp and the text. It does not cover the region tag in the header, and there are no fields for kind, severity, expiry, ID or status.

1.2 Who can send Verified

  • Anyone can send to #bulletin. Trust is decided only by the receiver.
  • In maarse-host, Command::SendChannel (node.rs, about line 1938) signs every message sent to the bulletin channel, using the host's own node identity (self.identity) and the system clock as the timestamp. There is no separate issuing step, no confirmation and no flags. If the text is too long, the send fails with "The message is too long".
  • The signing key is the same Ed25519 identity the node uses for announces, direct messages and its address. At start-up the host prints it as the "Bulletin key (for --bulletin-key on receivers)" (main.rs, about line 497).
  • The host joins #bulletin by itself only when it has trusted keys. A user can also join it by hand from the web client's hashtag dialog. After that, everything they type on that channel is signed. Inferred
  • Access to the host's web client needs an access token (web::access_token), which is the only gate in front of signing. Verified

1.3 How receivers verify and trust Verified

  • maarse-host --bulletin-key <128 hex> (repeatable) adds a PublicIdentity (32-byte signing key plus 32-byte DH key) to bulletin_keys and joins #bulletin.
  • Node::on_bulletin calls bulletin::verify(from, plain, trusted). That function requires the channel sender address to be one of the trusted identities and the signature to match that identity's key. On success the host shows the text as "[Verified bulletin] " + text through the normal Event::ChannelReceived, and forwards the same string to MQTT. On failure it logs "dropped an unverified message".
  • Tests: bulletin::tests::round_trip_and_rejections (untrusted key, impersonation, tampering, wrong signer) and node.rs bulletin_tests::only_trusted_bulletins_are_shown and no_bulletin_channel_without_keys.
  • Key distribution: by hand, as a hex string on the command line. There is no hierarchy, certificate, expiry, scope, revocation or name. Trust is flat: any trusted key can say anything about anywhere.

1.4 Replay, expiry, duplicates Verified

  • Verified.timestamp is returned but never used by on_bulletin. No age limit, no future limit, and no memory of bulletins already shown.
  • The only duplicate filter is the router's flood DedupCache (maarse-core/src/dedup.rs): an FNV-1a hash of type, destination and payload, kept in a ring buffer. It catches the same packet bytes while they are still in the ring. Re-sealing the same signed plaintext with a new 8-byte nonce gives a new packet ID, which receivers show again. Anyone can re-seal, because the channel key is public. Inferred

1.5 Priority on the air Verified

  • qos::priority_with(packet, bulletin::channel()) raises any Channel packet whose destination is the bulletin channel from PRIO_CHANNEL to PRIO_DIRECT. The firmware radio loop does this (firmware/common/src/radio.rs, let urgent = maarse_crypto::bulletin::channel()), and so does the simulator.
  • The boost is based only on the destination address in the clear header. Repeaters do not verify, so unsigned junk sent to #bulletin gets the same priority as a real alert. Inferred
  • Duty-cycle limits apply as usual (duty.rs, 10 % per hour by default).

1.6 Area targeting Verified (simulator only)

  • docs/denmark/AREA-ALERTS.md is a proposal. It puts 'A' | id (u16) | kind (u8) | area | text inside the signed text, so the area is authenticated with the message. Kinds are 0 info, 1 evacuation, 2 fire, 3 flood, 4 water. The area is a circle (13 bytes) or a polygon of 3–12 corners.
  • maarse-sim-wasm/src/engine.rs send_alert builds exactly that layout and signs it with the real bulletin::sign, using one simulated authority. Receivers run the real bulletin::verify and test whether they are inside the area. The simulator sends the signed plaintext without the channel seal, a simplification that saves 40 bytes compared with the real system.
  • Flood limiting: either the existing regions (send_channel_in with the region that contains the area, else dk), or a simulator-only "area scope" in which forwarders more than AREA_MARGIN_M = 15 km outside the area drop the alert. Over backbone trunks, "alerts and bulletins always cross".
  • Nothing of this is in maarse-core, the host, the firmware or the clients.

1.7 How clients show it Verified

  • Web client (maarse-client/index.html): no bulletin-specific code. A verified bulletin from a host is an ordinary channel line that starts with the text [Verified bulletin]. There is no sound, banner, issuer name, severity or area. (The ✓ "verified" mark in the client is for contact key fingerprints, not bulletins.)
  • Firmware companion (firmware/common/src/node.rs, PacketType::Channel): decrypts any joined channel and emits ChannelReceived with no bulletin check. If a phone user joins #bulletin while connected directly to a radio, forged plain text is shown as-is under "#bulletin", and real signed bulletins show as binary junk. Inferred
  • Android: the GUIDE lists verification "without a host" as not done yet.

2. Gaps found in the code

#GapWhy it matters
G1Signed timestamp never checked; no alert ID; dedup only by packet bytesAny old bulletin can be replayed forever by re-sealing it ("Evacuate zone 3", months later).
G2No expiry, no update/cancel, no reference to an earlier alertNo safe "all clear"; an alert never ends; a correction can't be tied to what it corrects (Hawaii took 38 minutes to correct).
G3No status field (actual / exercise / test)Tests and drills look identical to real alerts. Hawaii's root cause was confusion about exactly this.
G4"Verified" is in-band text [Verified bulletin]Anyone can type that prefix on public or any other channel, and the client will show it the same way. The trust mark must come from the UI, never from the message.
G5Signing key = node identity; host auto-signs everything typed on #bulletinCompromising an always-on PC or its web token gives full alert power. An operator who types into the wrong chat sends a signed alert. No confirmation, no second person.
G6Flat trust list, no scope, no names, no expiry, no revocationA local volunteer's key can issue a nationwide evacuation. A stolen key stays valid until every receiver edits its command line.
G7Priority boost without verificationA LoRa attacker can flood #bulletin with junk at PRIO_DIRECT, pushing out direct messages and real alerts within the 10 % duty budget.
G8Firmware, Android and web client do not verifyOnly host users are protected. Direct-to-radio users either see nothing or see forgeries.
G9Region tag and (proposed) area scope are outside the signatureA relay can rewrite the header region to stop or widen the flood. That does not forge content, but it lets a relay suppress the alert.
G10No severity or event type → no presentation rulesEither every bulletin is loud (alert fatigue) or none is.
G11No audit trail of what was issuedAfter an incident nobody can show who sent what and when.
G12Nodes without a clock (firmware gets time only from the client, SetTime; boot_unix is None until then)Expiry and certificate validity can't be checked on standalone repeaters. The design has to work without wall-clock time.

3. Real-world systems External

3.1 Cell broadcast: 3GPP PWS, EU-Alert, ETWS, CMAS/WEA

  • Mechanism. 3GPP TS 23.041 defines the Cell Broadcast Service and the Public Warning System. An alerting authority sends to a Cell Broadcast Centre (CBC), which tells the radio network to broadcast in chosen cells. Phones don't need to be registered or subscribed, and the network learns nothing about recipients. That gives fast, privacy-preserving mass reach without congestion (TS 23.041; BRS on S!RENEN: "the authorities do not receive data about recipients' mobile phones and location").
  • EU-Alert. ETSI TS 102 900 is the European profile of cell broadcast; "EU" is replaced by a country code (NL-Alert, DE-Alert, and so on) (ETSI TS 102 900 V1.3.1, latest V1.4.1, 2023-06; overview). Article 110 of the European Electronic Communications Code (Directive (EU) 2018/1972) obliged member states to have mobile public warning by June 2022 (EECC).
  • ETWS (Japan). A two-stage design: a tiny primary notification (warning type only, delivered within seconds through paging) and a secondary notification with text over cell broadcast. TS 23.041 even defines a Warning-Security-Information field (timestamp plus digital signature) for the primary notification, but the spec now says the CBC should not include it. In practice, cell broadcast has no end-to-end authentication (TS 23.041 draft V19, clauses 9.3.25 and 9.4.1.3.6). 3GPP studied signatures again in TR 33.969 (Rel-17), where signature size and key distribution were central obstacles (TR 33.969; ETSI copy).
  • WEA (US). Categories are National (formerly Presidential, cannot be switched off), Imminent Threat (Extreme/Severe), AMBER, Public Safety, and tests. Since 2019 messages may be 360 characters (90 for older phones), and geotargeting must reach 100 % of the target area with at most 0.1 mile overshoot, which relies on phone-side geofencing (NWS summary of the FCC rules; FCC order 2018).

3.2 Denmark: S!RENEN and sirens

  • S!RENEN is Denmark's EU-Alert implementation over cell broadcast. It was launched and tested nationally on Wednesday 3 May 2023 at noon (Ministry of Foreign Affairs circular). It works on all compatible phones in the area, including foreign SIMs, with no app, in Danish and English, with a distinct sound. It is "a supplement to other warning systems" (BRS).
  • Beredskabsstyrelsen (DEMA) runs it with the National Police, which is reported to be its only sender (Wikipedia, secondary). That is a narrow, well-defined issuer set, the same property the 2019 spoofing paper recommends for signatures.
  • Denmark also has outdoor sirens and broadcast radio (DR) as warning channels. Må:rse should present itself as a supplement for when mobile networks and power are down, not as a replacement.

3.3 Germany: MoWaS, NINA, KATWARN, DE-Alert, Warntag

  • MoWaS (since 2001, run by the BBK) is the hub: authorities issue once, and MoWaS feeds apps (NINA, KATWARN), broadcasters and, since 23 February 2023, cell broadcast as DE-Alert (overview; Berlin.de; Telekom). BBK describes cell broadcast as one part of a "warning mix".
  • Warntag 2020 failed. The ministry attributed it to "an unplanned simultaneous triggering of a large number of warnings through MoWaS". Many warnings arrived very late (widely reported as around half an hour for NINA) or not at all (netzpolitik.org). The lessons are to test end to end under realistic load, to keep one message from one issuer instead of many parallel copies, and that apps alone are too slow. The 2021 Ahr valley flood then drove the move to cell broadcast.

3.4 Netherlands: NL-Alert

  • Cell broadcast, decided in 2008 after population trials in 2005–2006, tested twice a year (NL-Alert). In the December 2025 national test, 92 % of residents aged 12 and over reported receiving it (secondary source citing the ministry's reach measurement). Regular, announced tests build both reach and recognition.

3.5 Japan: J-Alert

  • A satellite-linked system (since 2007) from national agencies to municipal receivers, which trigger loudspeakers and community radio automatically. JMA earthquake and tsunami alerts reach phones through ETWS (overview; PreventionWeb). The lessons are a dedicated channel that doesn't depend on terrestrial networks, automatic local re-broadcast, and fixed, pre-defined message types.

3.6 US IPAWS and CAP signatures

  • Only approved alerting authorities can send. They sign a Memorandum of Agreement, complete mandatory training, receive a COG ID and a digital certificate, and their alert software signs every CAP message. The signature travels with the message so that downstream systems can verify the signing official and that the content is unaltered. Certificates must not be shared and are renewed (reported three-year cycle, with a monthly test requirement in some state guidance) (FEMA sign-up; IPAWS toolkit 2016, archived).
  • CAP 1.2 (OASIS, 2010) is the common alert vocabulary: identifier, sender, sent, status (Actual / Exercise / System / Test / Draft), msgType (Alert / Update / Cancel / Ack / Error), references, scope, and per info: category, event, urgency, severity, certainty, expires, senderName, headline, and area (polygon, circle, geocode). It allows an enveloped XML-Signature on the alert (CAP 1.2). The vocabulary is excellent. XML-DSig is far too large for LoRa, so Må:rse should map the fields, not the encoding.
  • The weakness: once a CAP message is turned into a broadcast (EAS audio, WEA, cell broadcast), the signature is dropped and the last mile is unauthenticated again.

3.7 Mesh and off-grid systems

  • Meshtastic. Since 2.5, nodes have public keys (PKC for direct messages). Admin commands are accepted only from up to three configured admin keys, with short-lived session IDs against replay (security docs; PKC blog). Keys are trust-on-first-use, and channel messages were unauthenticated. The docs describe optional XEdDSA-signed broadcasts with a default policy that still accepts unsigned packets. An advisory shows that someone who knows a channel key could inject direct messages that were displayed as PKC-encrypted (GHSA-377p-prwp-4hwf / CVE-2025-53627). That is the same UI-trust problem as our G4. I found no authority-based alert mechanism.
  • MeshCore. Adverts are Ed25519-signed over the public key and a timestamp (eastmesh wiki). Room servers are store-and-forward boards with a password-based admin ACL. I found no signed authority bulletin.
  • Reticulum / LXMF. Announces are self-authenticating (they carry the key and an Ed25519 signature). LXMF messages carry a 64-byte Ed25519 signature over destination, source, payload and ID, with a total overhead of about 99 bytes (LXMF). There's no authority hierarchy, but it shows that a signature per message is affordable on LoRa.
  • goTenna. I found no public technical documentation of an authenticated alert feature in the time available, so it is left out.

Conclusion for this section: none of the hobby LoRa meshes has authority-signed, scoped alerts. Må:rse's signed bulletin is already ahead of them. The gap is in lifecycle and governance, not in the basic crypto.

6. Threat model for Må:rse

Assets: the public's belief that a "verified" alert is real; the ability to deliver real alerts quickly; and airtime. Assumptions: Ed25519 and SHA-256 are sound; a radio attacker can transmit and receive any LoRa packet on our settings; the channel key for #bulletin is public, by design.

ThreatTodayAfter the recommendations

Replay of an old real alertWorks (re-seal with a new nonce).Rejected: per-issuer serial high-water mark, expiry, ID-based dedup (R2).
Flooding / DoS of the alert channelJunk on #bulletin gets PRIO_DIRECT.Only verified alerts are boosted; unverified traffic is demoted and rate-limited; per-issuer rate cap (R6). Jamming remains possible (out of scope; mitigated by repetition and backbone).
Fake "all clear"No cancel exists; a forged text "all clear" is blocked by the signature, but a trusted key can say anything.Cancel must be signed by the same issuer (or one whose certificate grants cancel), must reference the alert ID, and needs the same approval level as the original (R5, R8).
Forged or confused test alertsNo status; tests look real.Signed status: Actual / Exercise / Test / System. Exercise and Test never ring loudly and carry a banner (R3).

7. Proposed design: alert v2

Principles: end-to-end signatures only (relays never add trust), one small packet per alert, certificates sent once and cached, works without a clock, and keeps the router unchanged where possible (still a channel message on #bulletin, so old repeaters forward it). Everything below is a proposal Inferred design.

7.1 Key hierarchy (at most two levels below the root)

Root key  (offline; 2-of-3 custodians; public key built into firmware/app/host,
 |         like the OTA release key in maarse-crypto/src/ota.rs)
 +-- Regional intermediate (optional; offline laptop; e.g. per region / beredskab)
      +-- Issuer certificate (short-lived, scoped; one per person or console)
           +-- Alert (signed by the issuer key, one packet)
  • Issuer key ≠ node identity. A separate Ed25519 key, ideally on a hardware token or at least a passphrase-protected file, used only for alerts. This closes G5 and keeps the node's everyday identity out of the blast radius.
  • Validity: 30–90 days for issuer certificates (short enough that revocation lists stay small), with "standby" certificates pre-issued to municipalities and kept offline for disasters. Intermediates are valid for 1–2 years.
  • Scope bound in the certificate: allowed event types (bitmask), highest severity, allowed status values, area bound (circle, or a list of region IDs), "may cancel others in scope", and "needs co-signature above severity X". The receiver checks that the alert lies inside the certificate's scope, and the intermediate's scope must contain the issuer's.
  • A short display name is part of the signed certificate (for example "Beredskab Østjylland"), so the UI can say who sent the alert. Names come from the root, not from the sender.

7.2 Certificate packet (about 156 bytes plaintext, sent once and cached)

0xC1 | ver (1) | subject Ed25519 key (32) | parent key id (8) | serial (4)
     | not_before (u32) | not_after (u32)
     | events bitmask (u16) | max severity (1) | flags (1: may-cancel, needs-cosign, status mask)
     | area bound: circle lat/lon i32 1e-5 deg + radius u16 x 100 m (10)
     | name length (1) + name UTF-8 (up to 24)
     | Ed25519 signature by parent (64)

Repeaters and clients store certificates they have verified (a few dozen at about 160 bytes each fits in flash). An alert whose issuer certificate is unknown triggers a small "certificate request" (issuer key ID, 8 bytes) that any node holding it answers, the same way key requests work today.

7.3 Alert packet (fits in one 255-byte packet with about 105–109 bytes of text)

0xB2 | flags (1): status 2b (Actual/Exercise/Test/System) | msgType 2b (Alert/Update/Cancel)
     |            area type 2b (none/circle/polygon/region) | has_ref 1b | lang 1b
     | serial (u32, per issuer, strictly increasing)
     | issued (u32 Unix s) | expires (u16 minutes after issued)
     | event (1: evacuation, fire, flood, water, chemical, shelter, info, ...)
     | severity 4b | urgency 4b   (CAP vocabulary)
     | [ref serial (u32) if has_ref]
     | area (circle 10 / polygon 1 + 8n / regions 1 + 2n)
     | text (UTF-8, or template id + parameters)
     | Ed25519 signature (64) over "maarse/alert/v2" | channel | issuer key id | all of the above
  • The issuer is identified by the seal's existing 16-byte sender field, set to the issuer key's address, so no extra bytes are needed for a key ID.
  • Replay: receivers keep, per issuer, the highest serial seen (persisted). Older serials are accepted only if not yet expired and not already shown (a small set). When time is known, reject issued more than 10 minutes in the future and anything past expires.
  • Trusted time floor for clockless repeaters: the newest issued of any verified alert or certificate is a lower bound on "now". Time never goes backwards, which is enough to reject expired certificates and very old replays.
  • Dedup by (issuer, serial) instead of packet bytes. Scheduled repeats (for example at T+0, +2, +10 and +30 minutes) are new packets but show once.
  • Cancel/Update carry ref serial. A cancel is valid only from the same issuer or from a certificate with "may cancel" and the area in scope. The UI shows "Cancelled by …" on the original and stops any repeating alarm.
  • Templates: a 1-byte template ID (for example "Evacuate the area now", "Stay indoors, close windows", "Boil drinking water") rendered in the phone's language, plus a short free-text tail. This saves airtime, supports Danish and English like S!RENEN, and makes typos and panic wording less likely.

7.4 Two-person rule (Hawaii lesson)

  • Step 1 (procedural, cheap): the issuing console requires a second operator to approve an alert with status Actual and severity Extreme, or with an area above a threshold. The console shows a preview and the area on a map. Exercise is a separate mode with a different colour, and in that mode the console refuses to send Actual.
  • Step 2 (cryptographic, optional): the certificate flag "needs co-signature" makes receivers require a second, small endorsement packet. It holds the alert issuer key ID (8), serial (4), alert hash (8) and the co-signer's signature (64): about 85 bytes plaintext, or 143 bytes on air. The alert is shown as "awaiting confirmation" or held until both arrive (policy choice).
  • Step 2b (no extra airtime): FROST threshold signatures (RFC 9591) produce one ordinary 64-byte Ed25519 signature from 2-of-n key shares. Receivers verify it exactly like today, and only the issuing consoles change. This is the cleanest long-term option, but it needs an interactive round between the two operators' devices and careful implementation, so use it only for the top class.

7.5 Revocation in the mesh

  • Self-revocation: at issuance, the issuer also signs a "revoke me" packet (key ID, serial, signature: about 70 bytes) and stores it offline. Anyone holding it can kill the key at once without the root. An attacker who steals the key gains nothing by revoking it.
  • Root or intermediate revocation list: signed list of revoked certificate serials (4 bytes each, about 31 per packet), with a list number. Repeaters store the newest list and re-flood it rarely (for example with their announce interval) and on request.
  • Short validity keeps lists short. Every list or revocation packet is itself signed, so a forged revocation is impossible.

7.6 Priority and rate limits on the radio

  • Repeaters already link maarse_crypto. They can derive the public #bulletin key, open the seal, and verify the alert and certificate chain before giving PRIO_DIRECT.
  • Verified alerts are forwarded first. Unverified traffic on #bulletin is forwarded at PRIO_BULK with a small per-minute quota, or not at all once the repeater has a root key. Keep a fallback so that a repeater with an old revocation list doesn't drop valid alerts.
  • Per-issuer cap (for example 6 alerts per hour forwarded per issuer, cancels exempt), so a stolen key can't drain the duty budget.
  • CPU cost: Ed25519 verification on the nRF52840 (64 MHz Cortex-M4) with the pure-Rust crate is estimated at tens of milliseconds, perhaps up to about 100 ms per signature (not measured). The firmware already verifies OTA manifests with ed25519-dalek. Cache verified certificates so that an alert costs one verification.

7.7 Area

  • Keep the AREA-ALERTS part 1 idea: the exact area goes inside the signed alert. The receiver decides loud (inside), quiet (nearby, for example within the 15 km margin) or not shown.
  • For flood limiting (AREA-ALERTS part 2), the bounding circle in a clear-text TLV must equal the signed area, and receivers must check that. A relay that edits it can only hurt reach, not content. Prefer verify-on-repeater (7.6) so repeaters can use the signed area directly and the TLV is only a hint for old nodes.
  • Receivers check alert area ⊆ certificate area. An approximation is enough: the alert's bounding circle inside the certificate circle.

7.8 Client display

  • A dedicated event (for example Event::AlertReceived, carrying issuer name, event, severity, status, area, expiry, cancel state and verification result) instead of a channel line. The UI draws the badge, so no text in any message can produce it.
  • Full-screen banner and sound only for Actual + Severe/Extreme + inside area. Quiet entry for outside area, Minor, Exercise and Test. Exercise and Test have a striped "EXERCISE" / "TEST" banner. Expired and cancelled alerts are greyed out.
  • Shows "From: Beredskab Østjylland (certificate valid until …), verified", hop count, time sent, and "time unknown" when the device has no clock.
  • Never render raw #bulletin traffic. Hide the hashtag join for #bulletin, or route it to the alert view with "UNVERIFIED, ignored".

10. Out of scope

  • Being an official public warning system or claiming the legal status of S!RENEN. Må:rse is a supplement for when cellular networks and power fail. Any official use needs an agreement with Beredskabsstyrelsen and the police.
  • Preventing jamming or physical radio suppression. We can only mitigate it with repetition, multiple paths (backbone, carry) and fast recovery.
  • Confidentiality of alerts. They are public on purpose. Encrypting them would only hurt reach.
  • Tracking recipients. Like cell broadcast, delivery should be one-way. Don't add read receipts for alerts.
  • X.509 and XML signatures on air. Far too large for LoRa. Use them only on the host's CAP side.
  • Post-quantum signatures. Even the smallest standardised ones (Falcon, about 666 bytes) do not fit in a packet. Revisit if needed, for example with hash-based certificates verified on the host side only.

11. Open questions for the owner

  1. Who should hold the root key: the project, a foundation, or a public authority? This decides whether alerts are "community" or "official".
  2. Should an alert whose co-signature has not yet arrived be shown (labelled) or held back? Holding back is safer; showing is faster.
  3. When a certificate has expired during a long outage, should receivers reject it, or show the alert with a warning? I suggest showing it with a warning for a short grace period, and only for issuers seen before.
  4. Should repeaters drop unverified #bulletin traffic completely, or only demote it?
  5. Which event types and templates do Danish users need first (evacuation, shelter in place, flood, water, fire, chemical, power, information)?
