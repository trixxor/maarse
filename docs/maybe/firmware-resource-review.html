Summary

The firmware is soundly built: fixed-size tables instead of free allocation (the heap serves the ESP32 radio drivers and the optional hotspot), size-optimised nRF builds, large objects placed in statics with care, and earlier stack problems fixed and documented. The weak spots are at the edges: nRF is out of flash, ESP32-S3 is short of stack while memory elsewhere lies idle, several things run far below what the hardware can do, and a field node cannot yet recover by itself from every fault.

The five findings that matter most

  • N3: a four-line change frees 4,032 B of nRF flash, almost four times today's WisMesh margin.
  • S1: the radio loop can throw away a packet it is receiving, on every board.
  • S2: node-to-phone Bluetooth uses 20-byte pieces where 244 are possible.
  • N2 and S3: an nRF node that panics stays dead, and no board has a watchdog.
  • E1-E4: ESP32-S3 speed and RAM are left on the table (clock, flash mode, SHA-512, two radio drivers).

What the comparison says

  • The two families have opposite limits. Spend RAM to save flash on nRF; spend flash to save RAM on ESP32. One shared set of table sizes and build habits cannot be best for both.
  • Same logic, very different footprint. The nRF build does the whole job in 388-396 KB of flash and 172 KB of static RAM. The ESP32 build needs about 1.3 MB and 66 KB of code in RAM, mostly vendor radio libraries.
  • Each family has learned lessons the other lacks. ESP32 restarts after a panic and runs SPI at 8 MHz; nRF times out a silent radio and uses compact SHA-2. Move them across.
  • Common code, common gains. S1 to S8 are fixed once in maarse-fw-common or maarse-core and help every board.
  • The two boards within a family differ little: choose per-board work only for E7 (Heltec display), E11 (XIAO PSRAM) and N6.

Shared findings (all boards)

S1 A queued packet or a timer throws away the packet being received

HighRead in codefirmware/common/src/radio.rs:248-333

The radio loop listens with select6. When a new transmit job arrives (even one with a delay) or the next planned time comes, the receive future is dropped and the loop calls prepare_for_rx or enter_standby. Both put the SX1262 in standby, so a packet that is half received is lost. The driver sees the preamble interrupt but ignores it (lora-phy, rx()). A 180 B announce lasts 955 ms at SF9, so the window is large, and in a flood a node's planned forward can easily fall while neighbours send their copies. How often it happens in practice is not measured.

Do: Keep the same receive future alive when the new job is not due yet. Before leaving receive mode, check whether a preamble or header has been detected and wait for the packet (limited by its longest airtime). Add a counter for aborted receptions first, so the size of the problem is known.

S2 Bluetooth sends 20 bytes per notification

HighRead in codeCalculatedfirmware/esp/src/ble.rs:21, firmware/nrf/src/ble.rs:18

CHUNK = 20 is fixed, while the Android app asks for an MTU of 247 and uses it in its own direction. A full 300-byte frame becomes 15 notifications instead of 2, and an 8 KB file about 410 instead of 34. This is the largest throughput limit between node and phone. The spectrum sweep already throttles itself because of it.

Do: Use the negotiated size (conn.raw().att_mtu() - 3, at most 244; it is 23 - 3 = 20 until negotiated). Test with the Android app and the web client over Bluetooth.

S3 No watchdog on any board

HighRead in codefirmware/*/src/main.rs

esp_hal::init disables the watchdogs and the nRF firmware never starts one. The nRF start-up code notes that the LoRa driver waits for the BUSY pin without a limit. A task that hangs leaves a repeater dead until somebody visits it.

Do: Start the hardware watchdog (30-60 s) and feed it only when the node task and the radio task have both made progress. Leave it paused in sleep.

S4 Settings and identity are erased before they are rewritten

HighRead in codefirmware/common/src/storage.rs:252-255

Every change (name, role, radio, Bluetooth pairing, counters) erases the one settings page and writes it again. Power lost between the two loses the node's identity and all settings. The contact, sensor and mailbox pages work the same way when they are compacted.

Do: Two pages with a sequence number and checksum, written alternately. There is room: nRF has pages 0xEF000-0xF3FFF unused, the ESP32 partition uses 24 of its 64 KB. On nRF, mind the flash margin (N1).

S5 8 KB of RAM is reserved only for mailbox compaction

MediumMeasuredCalculatedMAIL_BUF in main.rs; node/files.rs

Three 8,193-byte buffers are always resident: mailbox, file out, file in (24,579 B). The spectrum recorder already borrows the file buffers. The mailbox buffer is used when the mailbox is compacted and when the sensor page is read (1,920 B of it), and radio nodes do not even offer a mail service.

Do: Borrow a file buffer when no file is moving, or compact page by page. Gain: 8 KB of RAM, which on the ESP32 is 8 KB more stack.

S6 The routing tables are the largest object in RAM (61,440 B)

S7 The node is built from temporaries on the stack

MediumMeasuredfirmware/common/src/node.rs:384-461

FwNode::new_in writes one large struct literal, so the compiler assembles parts of the 32 KB node on the stack first. Its frame is 42,416 B on ESP32-S3 and 12,744 B on nRF52840. It runs once, but on the ESP32-S3 it probably sets the highest stack mark since boot, and every kilobyte of static RAM is taken from the same space.

Do: Initialise the large fields in place (addr_of_mut!, or per-field init functions for known, sessions, sensor). The free-stack gain is limited by whatever is the next deepest path, so print the stack mark right after start-up, after the Wi-Fi start and after remote commands to see which one rules.

S8 Nothing stops a build from eating the last margin

MediumRead in codefirmware/nrf/build.rs, firmware/nrf/src/ota.rs, CI

The WisMesh linker allows 401,408 B, but an over-the-air update accepts only 397,312 B. An image between the two links without any warning and can then not be installed over the air. On ESP32 nothing fails when the stack shrinks; the notes record a hang and a crash from exactly that. nRF also does not report unused stack.

Do: A small check in CI and the build script: nRF image at most 397,312 B minus a margin, ESP32 .stack at least a set value. Add stack painting on nRF when flash allows (or use flip-link, N2).

nRF52840 findings

N1 Flash is nearly full

HighMeasured0x26000/0x27000 to 0x88000

WisMesh Tag: 395,810 of 397,312 B, 1,502 B left (0.4 %). XIAO nRF52840: 387,618 B, 9,694 B left (2.4 %). Any ordinary feature will break the WisMesh build for over-the-air updates. N3 is the cheapest way out.

N2 A panic or fault stops the node for good

HighRead in codefirmware/nrf/src/main.rs:42

panic_halt loops forever, and the default HardFault handler does too. The ESP32 firmware restarts for exactly this reason. A stack overflow is also silent here: the stack grows down into static data.

Do: A panic handler and a HardFault handler that call SCB::sys_reset() (tens of bytes), plus the watchdog (S3). Link with flip-link so an overflow faults instead of corrupting variables (no flash cost).

N4 SPI to the radio runs at 1 MHz

LowRead in codeCalculatedfirmware/nrf/src/main.rs:241

The ESP32 firmware uses 8 MHz. A full 255 B packet takes about 2.0 ms instead of 0.26 ms, during which the node cannot do the next radio step. Small next to LoRa airtime, but it shortens the gap between listen-before-talk and transmit and the spectrum sweep. An earlier problem at 8 MHz was with SPIM3; the firmware now uses SPIM2.

Do: Try 4 and 8 MHz on both boards and run tools/radio_test.py. Keep 1 MHz if anything is unstable.

N5 Flash writes stop the CPU while Bluetooth runs

MediumRead in codefirmware/nrf/src/storage.rs, ota staging

The settings code uses the NVMC directly. A page erase halts the CPU for up to about 85 ms, and the Bluetooth library (MPSL) is not told. Lost Bluetooth events are possible during saves and during an update download; this review did not test for it.

Do: Use nrf_mpsl::Flash, which does the work in radio time slots. It costs some flash and makes the storage calls asynchronous, so weigh it against N1.

N6 USB and the 32 MHz crystal stay on without a cable

MediumRead in codefirmware/nrf/src/main.rs:299-333

Unless a sensor recipe sleeps, the high-frequency crystal is requested for good and USB starts with SoftwareVbusDetect(true, true), also on battery. That matters for the WisMesh Tag. The XIAO build also uses the internal RC oscillator and does not switch on the DC/DC converter.

Do: Start USB and request the crystal only while USB power is seen (battery::vbus_present() already exists). Check the XIAO schematic for the 32 kHz crystal and DC/DC parts. Measure current before and after.

N7 Code the board cannot use is still built in

LowRead in codeEstimatefirmware/common

The common crate has no board features, so the nRF image carries Wi-Fi modem handling, Wi-Fi settings storage, network queues (NET_RX, NET_TX, NET_STATS) and display bookkeeping; the XIAO also carries GPS code. The saving has not been measured; a few kilobytes of flash and about 3-4 KB of RAM is a fair expectation.

Do: Add wifi, display and gps features to maarse-fw-common and measure.

N9 Long term: half the app space is the update staging area

LowMeasuredCalculatedfirmware/nrf/src/ota.rs

App and staging area split the space about equally. Today's images compress to 75 % (zlib), 78 % (deflate with a 1 KB window) and 67 % (LZMA). Staging a compressed image would allow roughly 46-72 KB more app (calculated, before the cost of the decompressor). The unused SoftDevice area (about 148 KB) is larger still, but taking it needs another bootloader.

Do: Keep as a plan for when N3 and feature gating are used up. It changes the update path, needs a transition for nodes in the field and can brick a node if wrong.

ESP32-S3 findings

E1 The CPU runs at 80 MHz, not 240 MHz

HighRead in codefirmware/esp/src/main.rs:234

esp_hal::Config::default() gives CpuClock::_80MHz (checked in esp-hal 1.2.2). All signatures, key exchanges, proof-of-work stamps and routing run at a third of the chip's speed. The note in stamp.rs assumes 240 MHz.

Do: Config::default().with_cpu_clock(CpuClock::max()), or 160 MHz as a middle way. CPU-bound work gets up to 3x faster (estimate); current draw goes up, so measure both and update the power profile used by the range test. A repeater on solar power may prefer 80 MHz: make it a conscious choice.

E2 Code is fetched from flash in DIO mode at 40 MHz

HighMeasuredCalculatedimage headers in dist/*.bin

Almost all code runs from external flash through a cache. The headers of both built images say DIO, 40 MHz. QIO at 80 MHz gives about four times the raw transfer rate on a cache miss (calculated).

Do: Pass flash mode and frequency to espflash in the build scripts (QIO, 80 MHz) after checking that both boards' flash supports it. The setting sits in the bootloader, so existing nodes need a USB flash; test boot, settings writes and an over-the-air update.

sha2::sha512::compress512 is 44,839 B; the instruction cache is 32 KB. Ed25519 signing and checking go through it, and code that cannot stay in the cache is fetched from flash again and again. With the compact rounds the nRF build already uses (tested in a copy):

E5 About 35 KB of the heap is idle while the stack is tight

MediumRead in codeCalculatedfirmware/esp/src/main.rs:241

The heap is 72 KB in memory the bootloader releases. The guide gives about 34 KB used by Bluetooth and 37 KB by Wi-Fi (48 KB with the hotspot). The Bluetooth controller also runs with its defaults: 6 connections and an 8 KB task stack, where one phone is served.

Do: First read the lowest free heap (statistics key 89) under load. Then shrink the heap to 55 KB and put 16 KB of buffers there with #[esp_hal::ram(reclaimed)] (the two file buffers): +16 KB stack. Lower the controller to 1-2 connections to widen the margin. Hardware test required.

E6 The stack margin has shrunk, mostly for the hotspot

HighMeasuredCalculatedlinker section .stack

The stack is whatever RAM is left. It was 65,520 B on 26 November, now 60,336 B (Heltec) and 62,792 B (XIAO). The last hardware reading on the Heltec was 9,296 B never used (earlier session, build with 60,720 B). The hotspot build has 52,456 B. The notes say the Wi-Fi driver's start needs about 51 KB and report 57 KB for that build: if the need is unchanged, about 1.4 KB is left (calculated, not tested at this commit).

Do: Do not ship the hotspot build before tools/stack_probe.py has run on it with Wi-Fi started. Then E3, E5, S5 and S7. This review did not trace the Wi-Fi start's call chain. The node's own start-up frame (S7) is of similar size, so print the stack mark before and after the Wi-Fi start to see which one sets the limit.

E7 Drawing the display blocks everything for about 0.1 s

HighRead in codeCalculatedfirmware/esp/src/main.rs:527, display.rs

(Heltec only.) The OLED uses blocking I2C at the default 100 kHz. Each redraw clears the picture, so all 1,024 bytes are sent, about 104 ms on the wire, once a second while the screen is on (2 minutes after a press, or always if chosen). All tasks share one core and one executor: radio, USB and Bluetooth wait.

Do: Set 400 kHz (one line, about 26 ms), draw only when the shown values change, and later switch the driver to asynchronous I2C so nothing waits.

E8 A silent radio stops start-up before USB exists

MediumRead in codefirmware/esp/src/main.rs:410-417

LoRa::new has no time limit and runs before the USB task is spawned. The nRF firmware wraps the same call in a 3 s timeout so the node stays reachable.

Do: Use the same with_timeout as on nRF.

E9 Flash access puts 4 KB buffers on the stack

MediumMeasuredesp-storage 0.10

FlashStorage::read and write have frames of 4,144-4,176 B, and the settings functions above them 3.2-4.8 KB. A save reached from deep inside message handling adds up to some 8 KB.

Do: Keep settings writes out of deep call chains (queue them to the top of the node loop), or use aligned, word-sized access so a smaller driver path can be used. Check the effect with the stack mark.

E10 Flash space and flags: plenty of room, wrong place to spend it

LowMeasuredfirmware/esp/partitions.csv

The Heltec app image is 1,383,520 of 2,097,152 B (66 %). opt-level = 3 was tried: 1,889,648 B (90 %), but the stack drops to 53,960 B (-6,376 B), so not for the whole firmware. The partition table ends at 4.1 MB: about 11.9 MB of the Heltec's flash and 3.9 MB of the XIAO's are not assigned. The Må:rse partition uses 24 of 64 KB.

Do: If speed is needed, raise the level only for the cryptography crates ([profile.release.package.curve25519-dalek] opt-level = 3) and measure. Use free flash for a larger mailbox, contact list and a crash log.

E11 PSRAM and the second core are unused

MediumRead in codeEstimatehardware

The XIAO ESP32-S3 has 8 MB PSRAM according to Seeed. For the Heltec V4 the sources disagree: Heltec's comparison lists an ESP32-S3R2 with 2 MB, but the test board reports only "WiFi, BLE, Embedded Flash" when flashed (seen again on 27 November, and recorded in docs/maybe/later-features.md), so it shows no PSRAM. The second CPU core is idle.

Do: Check each board with espflash board-info. Where PSRAM exists, the routing tables and file buffers (about 77 KB) can move there; they must not be used while flash is being written. That means two memory layouts unless the Heltec has it too. Leave the second core for later.

Method and limits

  • Release builds with the project's profiles, a placeholder release key (so the update code is included) and version 0.9.11, in a separate build folder. The Heltec app image came out at the same size as the one in dist/.
  • Toolchains: rustc 1.99.1 (nRF), esp 1.97.0-nightly (ESP32-S3). Sizes from llvm-readobj and llvm-nm; stack frames from the function prologues in the disassembly; structure sizes from -Z print-type-sizes on the nRF target.
  • The experiments in N3 and E3 changed source or dependencies in a throw-away copy only.
  • Not done in the analysis: no current, timing or throughput measurement; the boards were only used to test the changes listed under Status. No stack high-water measurement was made in this review. Hardware readings quoted come from earlier project notes and are marked as such.
  • A stack frame is the space of one function. The real worst case is the deepest chain plus interrupts, which static reading does not give.
  • Not covered: the MeshCore gateway firmware (C++, built from MeshCore), and the radio protocol's airtime use, which docs/maybe/airtime-optimisation.md already treats.
